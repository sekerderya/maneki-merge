# Maneki Merge: Technical Spec

## 1. Platforms and distribution

| Target       | How players install it                                                                                                  | Notes                                                                                                                                                                                                    |
| ------------ | ----------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| iOS / iPadOS | Safari (or any iOS browser) → Share → **Add to Home Screen**. It opens full screen from its own icon and works offline. | No App Store, Apple developer account, Mac, or re-signing every 7 days. Home-screen web apps keep their storage. No Vibration API. Orientation lock isn't honoured, so a rotate overlay is used instead. |
| Android      | Chrome → **Install app**, which puts a WebAPK in the app drawer. An APK via Capacitor is optional (M14).                | Vibration works, and so does the manifest's orientation lock.                                                                                                                                            |
| Desktop      | Any modern browser                                                                                                      | For development and testing.                                                                                                                                                                             |

Why a PWA: the owner builds on Windows and won't publish to the App Store. Native iOS builds need macOS and Xcode, and apps sideloaded with a free Apple ID expire after 7 days. A PWA installs on both platforms from one URL, updates itself, and runs fully offline.

Hosting: GitHub Pages from the public repo `sekerderya/maneki-merge`. It's free and served over HTTPS, which service workers require. Live URL: https://sekerderya.github.io/maneki-merge/

## 3. Architecture

```
src/
  main.ts            boot order: fonts and cat art → save → UI → Phaser → service worker
  session.ts         composition root for play: starts runs, wires run events to the HUD,
                     overlays and hints, owns pause / game over / quit (no rules)
  feedback.ts        maps a run's events to sounds and haptics (composition only)
  config/            pure data: app, platform, tiers, stages, upgrades, economy, physics, timings,
                     catArt (the lucky cats as vector shapes), skin (placeholder and jar colours)
  core/              pure rules: rng, dropQueue, economy, upgrades, progression, save, events,
                     profile (the save in play: wallet, records, stats, purchases, throttled
                     writes), shop (what each shop card shows)
  physics/           matter-js wrapper: PhysicsWorld (+ FixedStepper), balls, merges, danger,
                     geometry (the jar, floorRestY), circleCollision (exact circle contacts,
                     the floor's rounded corners)
  run/               RunController: the whole run, headless (drop, cooldown, queue, combo,
                     stage clears and the expansion timeline, jackpot, Lucky Save,
                     game over);
                     profileRun (a run banking into the profile and keeping its records)
  game/              Phaser: GameScene, cameraFit + aim + expansionView (pure math),
                     BallRenderer, JarView, PawView (the dropper's paw), paint (vector art into
                     canvas textures), skins/ (BallSkin, CatSkin, PlaceholderSkin, skinSets),
                     fx/ (MergeFx, PopFx, SparkFx), shake (pure camera shake)
  ui/                DOM: screens/ (menu, game), panels/ (shop, settings), overlays/ (pause, game over),
                     hud/, banners/ (banners, combo, hints), fx/ (coin flights), scenery (the shrine
                     garden behind the jar), styles/
  audio/             AudioEngine (context, unlock, mixer, limiter), sfx recipes, pitch,
                     throttle (per-sound and global voice limits)
  platform/          storage adapter, haptics, visibility, back button, orientation,
                     install hint, update badge, safe areas
  debug/             debug panel, window.__game hooks
tools/
  simulate.ts        headless balance simulator (M10, set aside in v0.10: not in the repo)
  build-art.ts       final art pipeline (M13)
tests/
  unit/  physics/  e2e/
```

Dependency rules, enforced with ESLint `no-restricted-imports`:

- `config` imports nothing except types (`import type` from `core`).
- `core` may import `config`. `physics` may import `config` and `core`. `run` may import `config`, `core` and `physics`.
- `config`, `core`, `physics` and `run` never import Phaser, DOM-only code, `game`, `ui`, `audio`, `platform` or `debug`. They must run in Node. They can't use browser globals (`window`, `document`, `navigator`, `localStorage`, `fetch`, …) or `Math.random`.
- Only `physics` (and `run` through it) imports matter-js.
- `tests/unit/layers.test.ts` lints snippets inside each layer to prove ESLint really blocks all of the above.

Randomness: `core/rng.ts` is sfc32 seeded through splitmix32. Its state is four unsigned 32-bit integers (`state()` / `Rng.fromState()`), and a unit test pins the sequence for one seed, so changing it is always deliberate. The caller picks the seed (`?seed=`, or a time-based one from the presentation layer).

- `game` and `ui` talk to each other only through the typed event bus (`core/events.ts`) and the RunController API, never by reaching into each other.

Data flow: pointer input (game) → `RunController.drop(x)` → PhysicsWorld steps → merge events → economy (score, coins) → wallet (`bank`, before the event) → event bus → HUD, FX, audio, haptics, records.

## 4. World, coordinates and camera

- The origin is the centre of the jar floor and y grows downward, so the rim is at `y = −H`. The jar is 600 × 870 world units at every stage: when the jar grows, the run rescales the world instead of building a bigger jar (below), so physics, gravity, speed limits, effects and line widths are the same at every stage.
- Jar geometry comes from `config/stages.ts` through `physics/geometry.ts` (`jarGeometry(stage)`: size, `rimY = −H`, dropper band, `dropY`), which the scene uses too. Walls are thick static rectangles (at least 300 units) so nothing can tunnel out. They rise `WALL_HEIGHT_FACTOR` (4) jar heights above the floor; only the part up to the rim is drawn, and the invisible rest keeps a pile that grows past the rim from spilling over. They never move.
- A cat's radius comes from its size at the current stage (`catRadius(tier, stage)` = `sizeRadius(tier − firstTier + 1)`, GAME_DESIGN §4). The physics world tracks each cat's size; `RunController.radiusOf(tier)` gives it to the scene (dropper, aim guide, pops).
- The dropper band above the rim is `0.18 × W` (`DROPPER_HEADROOM_RATIO`), and a dropped cat starts at its middle, `dropY = −(H + 0.09 W)`, so the biggest dropped cat (size 4) starts above the rim. The drop x is clamped so the whole cat is inside the walls.
- The screen is split into bands: HUD (safe-area top + about 72 CSS px), the play band, and the safe-area bottom.
- Camera fit (`game/cameraFit.ts`): show [jar W + 2 × side margin] × [jar H + dropper headroom (0.18 W) + floor margin] inside the play band, letterboxed. Since v0.14 the canvas fills the whole screen and the DOM HUD floats over its top; the play band is the canvas below the HUD (`insetTop`: the HUD's bottom, measured by the game screen and re-read whenever the HUD resizes). The side margin is 0.15 W per side (the bamboo frame and the garden beside it: a 300 px jar on a 390 px phone, as in the owner's chosen screen) and the floor margin 0.2 W (the feet and the rug) (`config/view.ts`). When the band is taller than that, `CAMERA_SPARE_BELOW_RATIO` (0.5) of the spare height goes below the floor and the rest above the dropper: on a 390 × 844 iPhone with the HUD down to 173 px the rim sits at 287 px and the floor at 722 px, where the design has them (unit-tested). Frames of the same shape get the same spare in pixels, so the floor never moves on screen while the jar grows. `GameView.onJarBox` reports the stage jar's box in CSS pixels whenever it moves; the garden behind the canvas follows it.
- **The stage loop** (GAME_DESIGN §7). Making the stage's last cat (size 10, from two 9s) clears the stage, and the jar grows by `STAGE_ZOOM = r(10) / r(1) = 168 / 28 = 6` into the next one. The zoom happens in the old world: the camera pulls back by STAGE_ZOOM while the drawn walls slide out and the rim rises. When it ends, `PhysicsWorld.setStage(next)` shrinks the world by 1 / STAGE_ZOOM around the floor's centre (`Ball.rescale`: position, velocity, radius, mass): the last cat becomes size 1 of the new stage, the jar is the same 600 × 870 jar again, and the camera's frame is the plain jar again. On screen nothing jumps. The last cat is the only cat left at that moment (the clear popped every other one), so the rescale is exact.
- The RunController owns the expansion timeline; every frame, the scene derives camera zoom and scroll plus the wall and rim visuals from it, so visuals and physics never drift apart.
  - `run.expansion` is `{ from, to, elapsedMs, progress (0–1 over EXPANSION_DURATION_MS, 2.1 s), zoomProgress (0–1 over EXPANSION_ZOOM_MS), phase }`, or null outside an expansion. It counts fixed ticks, like everything else in the run.
  - Stage clear (the tick the last cat is made, after the merge's own events): every other cat pops into its value (`catPopped { id, … }`, reason `cashOut`, oldest first, then `runCoinsChanged`), `stageCleared { stage, tier, next }` fires, and the state becomes `expanding` with phase `clear` (every stage is open since v0.12); at the last stage (`next: 'final'`) play goes on.
  - Phase `clear` (EXPANSION_CLEAR_MS, 0.5 s): no input; physics keeps stepping (merges aren't resolved, the danger timer is reset) so the last cat finishes growing and settles alone. Play time advances.
  - Phase `zoom` (EXPANSION_ZOOM_MS, 1.2 s): `expansionStarted { from, to }` fires and the physics world pauses (time stop): play time, the drop cooldown and the combo window freeze.
  - Phase `reveal` (EXPANSION_REVEAL_MS, 0.4 s): the world is rescaled into the new stage, the drop queue moves to the new pool (each queued cat keeps its size), and `expansionRevealed { stage, newTiers }` fires (`newTiers`: the tiers the stage adds, up to its last cat). Physics stays paused.
  - End: physics resumes, the danger timer resets again, `expansionFinished { stage, newTiers }` fires, and `dropReady` announces the dropper's cat. A debug jump (`jumpToStage`) clears the next stage right away, one stage at a time.
  - `instantExpansion` (tests) runs the whole sequence inside one tick.
  - While the danger timer runs, `dangerTick { secondsLeft }` fires each time the countdown reaches a new whole second (3, 2, 1), for the tick sound and the countdown pulse.
  - While the run is paused (backgrounding, rotation, the pause button) the timeline stands still with it and continues from the same tick.
- **Expansion visuals** (`game/expansionView.ts`, pure, unit-tested). No Phaser camera effects or tweens: they run on the wall clock, would drift from the tick timeline and ignore pauses. Every frame the scene computes two frames from `run.expansion` and `run.renderAlpha`:
  - Zoom progress `t = (elapsedMs − EXPANSION_CLEAR_MS + alpha × PHYSICS_STEP_MS) / EXPANSION_ZOOM_MS` during the zoom (0 during the clear, 1 at the reveal). `renderAlpha` is the fraction of a tick the frame's leftover time has reached (`FixedStepper.alpha`), so the zoom moves smoothly at 60, 90 or 120 Hz and through rAF jitter instead of stepping in whole ticks. It only affects rendering.
  - The camera fits the jar grown by `STAGE_ZOOM^easeInOut(t)` (`growFrame`): the frame grows by a constant ratio per moment, which looks like an even zoom even across a sixfold change. The drawn walls and rim use `STAGE_ZOOM^wallProgress(t)` with `wallProgress = easeInOut((t − EXPANSION_WALL_LAG) / (1 − EXPANSION_WALL_LAG))` and a lag of 0.25: the view pulls back first, then the walls slide outward and the rim rises into the new frame. The jar always stays inside the camera frame, both arrive together when the zoom ends, and the floor never moves on screen (unit-tested). A lag of 0 locks the jar to the frame.
  - The physics walls never move; nothing moves during the zoom (time is stopped), and at the reveal the rescaled world matches the zoomed-out view exactly (headless test: nothing escapes, launches or jumps through four stage clears under a pile).
  - The stage clear's pops show each popped cat's own sprite (`BallRenderer.detach`) growing and fading with a ring and a gold "+coins" (`PopFx`); pops of one tick go off 30 ms apart, within 240 ms in all, so they end before the zoom. The zoom start bursts gold sparks along the rim (`SparkFx`, one pooled Phaser emitter, paused with the run), and so does the reveal.
- Resize or rotation re-fits the camera immediately, without a tween, also in the middle of an expansion: the frame is recomputed from the timeline every frame.

## 5. Physics

- matter-js engine with a fixed timestep of 1/120 s and an accumulator (at most 5 substeps per frame). Physics never depends on frame rate.
- **Exact circle contacts** (`physics/circleCollision.ts`). Stock matter-js treats every body as a polygon and runs SAT on its vertices: with 150 cats SAT took 55–65% of a step, and polygon cats roll over facets (a 20-gon won't roll on slopes under ~9°). `installCircleCollisions()` wraps `Matter.Collision.collides` once: a cat–cat pair uses an analytic circle test and a cat–wall pair a circle-vs-axis-aligned-box test, each with one contact point midway through the overlap; every other pair keeps SAT. A cat's body is still a polygon (12 sides drawn around the circle) because matter-js needs vertices for its broadphase bounds, but its mass and inertia are set from the true circle. The returned record follows matter-js 0.20.0's internal contract (record reuse through the pairs table, `bodyA` = smaller id, normal from bodyB to bodyA, one persistent support point so warm-starting carries over), so matter-js is pinned to exactly `0.20.0`, and tests check the contract and agreement with SAT before any upgrade.
- Constants in `config/physics.ts`, as chosen in M4 and retuned for feel in v0.12 and v0.13. Speeds are world units per second; the world has the same scale at every stage (§4), so none of these change with the stage.

  | Constant                                        | Value            | Why                                                                                                                                                                                             |
  | ----------------------------------------------- | ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | `PHYSICS_STEP_MS`                               | 1000 / 120       | At the speed cap even the smallest cat (size 1) moves less than its radius per step (unit-tested), and a step is cheap (0.8–0.9 ms with 150 cats).                                              |
  | `PHYSICS_MAX_SUBSTEPS`                          | 5                | Covers frames down to 24 fps; a longer frame slows the game down instead of spiralling.                                                                                                         |
  | `POSITION_ITERATIONS` / `VELOCITY_ITERATIONS`   | 10 / 8           | Overlap stays under 15% in the stress test. 16 / 12 didn't reduce overlap or pile creep reliably (M4 tried 20 / 12: 40% more cost).                                                             |
  | `BALL_FRICTION` / `BALL_FRICTION_STATIC`        | 0.05 / 0.2       | v0.13 (owner: "push each other more easily", a second time): cats slide and roll past each other instead of gripping (M4 had 0.2 / 0.5, v0.12 0.1 / 0.3).                                       |
  | `JAR_FRICTION` / `JAR_FRICTION_STATIC`          | = the cats'      | matter-js gives a pair the lower friction and the higher static friction of its bodies; until v0.12 the jar kept matter-js's 0.1 / 0.5, so the floor gripped harder than the cats' values said. |
  | `BALL_RESTITUTION`                              | 0.25             | Cats bounce a little off each other and off the walls.                                                                                                                                          |
  | `FLOOR_RESTITUTION`                             | 0                | v0.13 (owner: "cats shouldn't bounce on the floor"): the floor forces its pairs' restitution (`physics/restitution.ts`), so a landing cat stops dead.                                           |
  | `BALL_FRICTION_AIR`                             | 0.01             | matter-js default. It slows a fall a lot (terminal speed about 3600 u/s at 120 Hz), which the gravity below accounts for, and it is what stops a cat rolling on the empty floor.                |
  | `ENABLE_SLEEPING`                               | false            | Sleeping bodies skip contact checks, so resting same-tier cats could miss a merge.                                                                                                              |
  | `GRAVITY_BASE`                                  | 2.15 (2150 u/s²) | v0.13 (owner: "a dropped cat reaches the floor in exactly 1 s"): from the dropper to the empty floor a size-1 cat takes 1.00 s, a size-4 0.99 s (unit-tested; v0.12's 900 u/s² took 1.6 s).     |
  | `BASE_DENSITY`, `DENSITY_EXPONENT`              | 0.001, 1         | Mass grows like r (M4: r^1.5, v0.12: r^1.4), so a small cat can shove a big one.                                                                                                                |
  | `BALL_HULL_SIDES`                               | 12               | The hull only feeds the broadphase bounds, so few vertices are enough.                                                                                                                          |
  | `BALL_INERTIA_SCALE`                            | 2                | Half matter-js's own 4: cats roll aside easily when pushed (v0.12 had 3).                                                                                                                       |
  | `MAX_SPEED_BASE`                                | 2400             | Above a natural fall from the dropper (about 1600 u/s at the floor), so it only catches launches; 20 units per step, under a size-1 radius.                                                     |
  | `GROWTH_NEIGHBOUR_MAX_SPEED_BASE`               | 500              | Neighbours of a growing cat are pushed but never launched.                                                                                                                                      |
  | `MAX_ANGULAR_SPEED`                             | 30 rad/s         | About 5 turns per second, a tier-1 cat rolling at 800 u/s.                                                                                                                                      |
  | `MERGE_SPIN_RIM_SPEED` / `MERGE_SPIN_MIN_SLIDE` | 80 / 20 u/s      | v0.13: a merged cat turns as if another cat had clipped it (below).                                                                                                                             |
  | `WALL_THICKNESS` / `WALL_HEIGHT_FACTOR`         | 300 / 4          | Nothing tunnels through, and a pile above the rim can't spill over (§4).                                                                                                                        |

- Timers count whole steps (`stepsFor(ms)`): 2.5 s is exactly 300 steps, so floating-point noise never moves a deadline. `FixedStepper` divides the accumulated time by the step instead of subtracting step by step, for the same reason.
- Density per size is `0.001 × r(1) / r(s)`, so mass grows like r instead of r². This limits mass ratios: the last cat is 6 times as heavy as the first, not 36 times.
- **Rounded corners** (v0.14, GAME_DESIGN §6). The floor body carries its shape on `plugin.roundedFloor` (flat top at y = 0, quarter circles of radius 112 around (±188, −112)), and its rectangle reaches up to the corners' centres so the broadphase pairs it with every cat that could touch a curve. `circleCollision.ts` tests a cat whose centre is inside a corner's quadrant (and that is smaller than the corner) against the curve, every other cat against the flat top; at the foot of a curve both give the same depth, normal and support point, and one cat–floor pair covers the whole floor, so a cat rolling onto a curve keeps its warm-started contact. A first version used a separate body per corner: switching pairs at the foot of the curve made the 150-cat pile restless, and its rectangle had to cover the curve for the broadphase. Walls stay boxes: a cat inside a curve can't reach them, and a cat at least as big as the corner never gets its centre into the quadrant (the walls and floor stop it first).
- **Corner grip** (`CORNER_GRIP` 0.85). Without it a cat landing on an empty curve kept the part of its fall along the curve and shot across the jar like a pendulum. On every step a cat touches a curve and no other cat, its speed and spin are multiplied by 0.85: it slides gently down and stops near the foot of the curve (a test drops a cat by each wall; four cats spawned across the floor, as in the Lucky Save e2e test, stay apart). Piles leaning on a curve are left to the physics.
- **Bounce per body** (`physics/restitution.ts`). matter-js gives a pair the larger restitution of its two bodies, so a bouncy cat would bounce off the floor as much as off another cat. `installRestitutionOverride()` wraps `Matter.Pair.update` once (matter-js 0.20.0 sets `pair.restitution` there on every step a pair is active, and `Pairs.update` looks the function up on each call): a body that carries `plugin.restitution` forces that value on its pairs. Only the floor does, with 0. A cat landing on a cat that rests on the floor hardly bounces either, because the floor absorbs the push.
- The v0.13 retune, measured headless against v0.12 (with v0.12 also on the dead floor where noted): a size-2 cat rolling at 600 u/s into a resting size-6 moves it 47 units instead of 21; a size-2 dropped into a 20-unit gap between two size-3s pushes them 397 units apart instead of 109 (71 on a dead floor); a size-3 dropped on a size-5's shoulder shoves it 170 units instead of 47. Most of it comes from the faster fall; the friction, inertia and mass changes roughly double it again. The cost is in the 150-cat stress pile: it gets under 75 u/s after 7–9.5 s instead of 3–4.5 s, its largest overlap is 8–13% instead of 4–5%, and a step takes 0.93 ms instead of 0.78. In play (a bot dropping every 0.75 s for up to 4 minutes, 4 seeds) cats that landed more than 3 s ago move at 2 u/s on average, as before, and none faster than 60 u/s.
- The v0.12 retune was measured headless against M4's values: a size-2 cat rolling into a size-6 one moves it 69 units instead of 48 (+45%), a size-2 cat dropped into a gap between two size-3s pushes them 243 units apart instead of 202 (+20%), a 60-cat pile still settles in about 4 s, and the stress, growth and chaos tests pass unchanged. The chaos runs also showed (with both the old and the new values, about once in 300 000 ticks) a light cat squeezed against a wall by a newly merged neighbour poking its centre a few units into the wall for one step, because matter-js only finds the wall contact on the next step; the chaos test allows exactly that (one tick, under half a radius).
- Gravity and the speed limits are the same at every stage: the world is rescaled at each expansion (§4) instead of growing. A grown world would break matter-js: its resting-contact threshold is an absolute speed, so stacks would turn jittery from stage 3 on.
- Merges (`physics/merges.ts`, run after every step):
  - The step makes one pass over matter-js's pair list, which with sleeping off holds exactly the pairs that overlap this step (`collisionStart` + `collisionActive`), once each. It records each cat's first contact and collects same-tier cat pairs.
  - Order: candidate pairs are sorted by (older cat id, younger cat id), so the oldest cats merge first. Our ids come from creation order, so the order never depends on matter-js internals.
  - One merge per cat per step: a pair with an already used cat is skipped. Three touching cats give one merge; the third can merge on a later step. New cats aren't in this step's pairs, so chains continue on the next step at the earliest.
  - Two of the stage's last cat (or bigger) make a Jackpot and vanish. Otherwise the new cat is born at rest exactly at the midpoint (v0.13; until then it took the parents' average velocity, capped at 400 u/s, and drifted off the midpoint), at the parents' size, and grows linearly into its own radius over `MERGE_GROW_MS` (120 ms, 15 steps). It inherits the earlier landing time, so a pile over the line keeps counting.
  - It starts to turn, as if another cat had clipped it (v0.13): its rim moves at `MERGE_SPIN_RIM_SPEED` (80 u/s), so a size-2 cat turns at 2.4 rad/s and a size-11 at 0.4 rad/s, and friction and air friction slow it down within a second or so; on the floor it rolls a short way. The direction (`mergeSpinDirection`) comes from how the parents met: two cats sliding past each other drag each other's rims and both turn the same way, so the new cat turns that way (a cat landing on the right shoulder of another turns clockwise). When they slide past each other slower than `MERGE_SPIN_MIN_SLIDE` (20 u/s), the parents' own turning decides, and if they don't turn, the parity of their ids.
- Growth without launches: linear growth has the lowest peak growth rate (about 1.5% of the radius per step). matter-js 0.20 removes overlap in its position solver by moving `position` and `positionPrev` together, so growth pushes neighbours without giving them velocity. On top of that, every cat touching a growing cat is capped at `GROWTH_NEIGHBOUR_MAX_SPEED_BASE`, and every cat on every step at `MAX_SPEED_BASE` and `MAX_ANGULAR_SPEED`. A test wedges a big pair between the walls under a settled pile and resolves every merge at once: upward speeds stay under 20% of the speed limit.
- Stability acceptance test (headless): 150 random cats of a stage's drop pool settle within 10 s of simulated time. They overfill the 600 × 870 jar, so the pile rises past the rim and leans on the tall walls. After settling, no cat has escaped, the largest overlap is under 15% of the smaller radius, and no cat moves faster than the clamp. "Settled" means every cat is slower than 5% of the speed limit (120 u/s since v0.13, 75 before) from that moment on (checked until 12 s), with speeds averaged over 0.1 s since v0.14. Resting cats show velocity jitter (a cat can read 150 u/s while its position stays within a unit); the taller, curved-bottom pile of v0.14 reads such single-step spikes often enough to fail an instantaneous check on some seeds, although its cats move no more than on the flat floor (over the 2 s after 10 s, the farthest cat moves 0.02–0.57 of its radius with the curves and 0.01–0.42 without, 6 seeds). With the 0.1 s average it settles in 2.2–9.5 s (flat floor: 2.3–8.4 s). Positions are checked separately, through overlap and wall penetration.
- Measured in M4 (dev machine, Node 24): a step with 150 settled cats takes **0.79 ms** on average (0.70 ms in v0.10's jar, 0.93 ms with v0.13's heavier, more slippery pile) (`npm run test:perf`, budget 2 ms; stock polygon SAT took about 1.8 ms). The stress test settles in about 4–7 s, with the largest overlap at 4–8% of the smaller radius, wall and floor penetration at 2–4%, and nothing escaping. matter-js passes, so planck.js isn't needed.
- Known: tall piles keep creeping. With 150 cats, a slip of 0.1–0.4 of a radius within half a second can still happen after 10 s. It comes from matter-js's soft stacking; higher friction and more iterations didn't remove it. In play, cats arrive one at a time and merge, so piles are smaller. Watch it in the M5 phone test.
- Determinism (`tests/physics/determinism.test.ts`):
  1. One seeded RNG per run, used only by the drop queue. Physics has no randomness, and the matter-js engine never calls its own random.
  2. Fixed ticks: `update(frameMs)` only decides how many ticks run. Every timer counts ticks, never frame time or the wall clock (`Common.now` only feeds matter-js metrics).
  3. Inputs apply between ticks, so a run is its seed plus (tick, input) pairs. The test records a run driven by random frame lengths and replays it tick by tick: `stateHash()` (FNV-1a over the exact float bits of the run and every body) matches at every checkpoint, through an expansion.
  4. Ordering uses our own cat ids. matter-js body ids are global per process, so two worlds get different ids, but matter-js only compares them; the test builds another world in between to prove it.
  5. Exact replays hold on one JS engine. V8 and JavaScriptCore may differ in the last bit of `Math.sin` and `Math.cos`, so a seed isn't guaranteed to replay bit for bit across browsers.
- If matter-js can't pass the stability test after tuning, switch to planck.js behind the same `PhysicsWorld` interface and record why here.

## 6. Rendering

- Phaser 4 with WebGL (Canvas fallback): a transparent canvas over a CSS background.
- High-DPI: the game uses `Scale.NONE`. `game/index.ts` sizes the canvas to the play band × min(devicePixelRatio, 2.5) (`MAX_RENDER_RESOLUTION`) and shows it at CSS size through the scale zoom (1 / resolution). A `ResizeObserver` re-fits it; the camera zoom is canvas pixels per world unit.
- The game loop sleeps (`loop.sleep()`) while the menu is visible and wakes when a run is shown.
- The `BallSkin` interface (`game/skins/BallSkin.ts`) gives a frame per tier, an optional upright number frame for the active stage (a tier's size depends on the stage) and the cat's main colour (merge particles, the pop ring). A frame is a texture key plus world units per texture pixel at the radius of the cat's size; that scale includes the hit-radius ratio. A number frame also says how far below the centre the number sits (`offset`, in radii, along the cat's own down axis): `BallRenderer` and the dropper put it there, rotated with the cat, but never rotate the number itself. Implementations:
  - `ArtSkin` (the default since v0.16, GAME_DESIGN §13.1): the nine raster looks in `public/assets/cats/` (`config/catSprites.ts`, data generated by `npm run art`, §14). Boot loads and decodes them with the fonts (`loadCatArt`; if they fail or take over 8 s, the game falls back to `?skin=vector`); each size gets one canvas texture at `CAT_PX_PER_UNIT`, scaled so the fitted body circle lands on the physics radius (big reductions go through halving steps). No numbers (`number()` returns null), so its textures are the same at every stage.
  - `CatSkin` (`?skin=vector`, the default in v0.11–v0.15): the nine looks of `config/catArt.ts` drawn with `Path2D` into canvas textures at `CAT_PX_PER_UNIT` (2.5). Each look is scaled so the outer edge of its outline (`bodyEdge`) lands on the physics radius; the ears poke out above it inside the texture. Numbers are drawn in the look's plate colours, with a thin outline in the plate's colour.
  - `PlaceholderSkin` (`?skin=placeholder`): circles and numbers drawn with the 2D canvas API, number offset 0.
    The canvas skins are refreshed after a WebGL context restore. `createGame(parent, skin)` picks the skin from the URL flag; the DOM icons follow it (`setIconSkin`).
- **Textures** (`game/skins/skinSets.ts`). The world has the same scale at every stage and the looks repeat with the sizes (GAME_DESIGN §13), so a size looks the same at every stage: the 10 body textures are drawn once, at 2.5 texture pixels per world unit (`CAT_PX_PER_UNIT`, `PLACEHOLDER_PX_PER_UNIT`), never upscaled on phones and tablets, and shared by every stage. Only the numbers differ per stage: each stage's set is its 10 tiers' numbers, drawn at their size's radius, the drop pool's first. Canvas textures get no mipmaps (Phaser 4.2 renders with WebGL1), so during the sixfold zoom-out the old stage's textures are shrunk a lot for about a second; at the reveal everything is back at its normal size.
  - `BallSkin.prepare(stage, budgetMs)` draws the next stage's numbers during the zoom, about 4 ms per frame (physics is paused then, so it costs no frames); `setStage(stage)` switches at the reveal (finishing anything missing) and bumps `revision`, and `BallRenderer` gives live sprites their new textures. The skin keeps stage 1's numbers (every run starts there) and the previous stage's, and frees the rest. Bodies take about 11 MB of texture memory with the lucky cats (size 10 alone is about 940 px square; 16 MB before v0.15 with size 11, 22 MB before v0.12 with size 12 and golden bodies).
  - Line widths: the jar's lines are fractions of its width (they grow with it during the zoom), and floating texts and the danger countdown render at the current zoom, so all of them keep their on-screen size and sharpness. The pop ring texture is 512 px, so a last cat's Jackpot ring isn't upscaled.
- Numbers are separate upright sprites in a layer above all bodies, so a 6 never looks like a 9.
- The jar (`game/JarView.ts`, art in `config/jarArt.ts`, v0.14): vector shapes (`config/paintShape.ts`: paths with fills, strokes, clips and linear gradients) drawn once with `Path2D` (`game/paint.ts`) into one atlas texture at `JAR_PX_PER_UNIT` (1.6) texture pixels per world unit, cut into pieces that only cover drawn parts: behind the cats the far rail and the feet; in front of them the two posts, the two curves and the bottom of the bamboo U frame with its nodes, ties and caps. The frame's inner edge is the physics jar, curves included. The jar keeps its shape while it grows (`scaleFrame`), so the pieces simply scale with it. Graphics layers draw the glass shine over the cats, the dashed danger line and, while the danger flash is on, red caps. The atlas is refreshed after a WebGL context restore.
- What doesn't move on screen is DOM, painted once: the wooden floor, the rug and the jar's shadow are part of the garden (§7), and the glass wash is a `div` placed on the jar (`gameScreen.setJarBox`). Only while the jar grows does the canvas draw the glass (and the DOM glass hide), because the jar moves then. Measured in the e2e setup (Pixel 7 emulation on a software WebGL renderer): whole-jar textures ran the game at 30 steps per second out of 120, the pieces at 40–60, and with the glass and rug in the DOM at 80–83, like v0.13's 86.
- The dropper's paw (`game/PawView.ts`, art in `config/pawArt.ts`, v0.14): the paw and the lower 440 units of the arm are a texture (2.5 px per unit); above it a Graphics layer draws the plain arm up to the top of the screen, whatever its height. The paw's bottom sits `PAW_GRIP` (0.72) of the cat's radius above the cat's centre; on `catDropped` it lifts by 26 units and settles back (`pawLift`, unit-tested). It is drawn over the cat and hidden during an expansion.
- Juice (M9, `config/view.ts`): every merge bursts particles in the new cat's colour from one pooled emitter (`SparkFx.mergeBurst`, tinted per burst) and bumps the new cat's sprite (`BallRenderer.bump(id)`, the `merged` event carries the new cat's id and size; particle counts, shake and the merge pop's pitch follow the size, so every stage feels the same). Camera shake (`game/shake.ts`, pure and unit-tested) is an offset added to the camera centre after the fit, so it never changes the fit or the expansion frames; a stronger shake replaces a weaker one and the pause clears it. The danger countdown pulses on each `dangerTick`. With reduced motion (`platform/motion.ts`: the setting or `prefers-reduced-motion`, read live): no shake, `REDUCED_MOTION_PARTICLES` of the particles.
- Draw order (Phaser layers): jar back (rug, glass, far rail), aim guide, cat bodies, numbers, jar front (frame) and rim, dropper (cat, then the paw), effects.
- `BallRenderer` matches pooled body and number images to cats by id every frame; merge pops, cat pops and floating scores (`MergeFx`, `PopFx`) are pooled and animated by hand. No per-frame allocations in hot paths.
- The aim guide is a dotted line from the dropper cat to the point where it first touches a cat or the floor (`game/aim.ts`; on a curve the floor is `floorRestY`), plus a faint ghost circle there. A unit test checks it against the real physics.

## 7. UI (DOM)

- `index.html` has `#menu-screen` and `#game-screen`, and only one is visible at a time. The Phaser canvas lives in `#game-screen`, and the scene sleeps while the menu is visible.
- Theme (GAME_DESIGN §13.1): CSS tokens in `ui/styles/tokens.css`. Buttons have a 3 px ink border and a solid ink edge below that they sink into when pressed; plates that only show a value (coins, records) have the border but no edge. Coral is reserved for the one primary action of a screen.
- Menu (`ui/screens/menuScreen.ts`): the scene is an inline SVG that covers the hero area (`preserveAspectRatio="xMidYMax slice"`, anchored to the ground, which continues below in `--color-ground`). The hero takes the height that is left (`flex: 1`); the cat's size comes from container query units (`min(58cqh, 176px, 46cqw)`, 150 px without them), and the halo, coins and cushion are placed in % of it.
- The HUD, overlays and banners are absolutely positioned DOM elements with `pointer-events: none`, except on controls.
- Since v0.14 the play area fills the screen (canvas, banners and hints) and the HUD floats over its top (`ui/hud/hud.ts`, GAME_DESIGN §2.3): the score card and the stage card on the left; the next cat (`run.next`) in its glass bubble (two inline SVGs, back and shine, around the cat icon), the pink pause button and the coins card on the right. The HUD has `pointer-events: none` except on the pause button, so touches over it still aim. The game screen measures the HUD's bottom for the camera (`hudBottom()`, re-read on resize through a `ResizeObserver`).
- The shrine garden (`ui/scenery.ts`) is one inline SVG behind the transparent canvas, built once from code (blossoms placed by a seeded `Rng`). It is drawn for the owner's 390 × 844 screen with the jar's inside at x 45–345 and its floor at y 722 (`SCENERY_JAR`, unit-tested against the camera fit), and `setJarBox` scales and moves it so that jar lands on the real one (`GameView.onJarBox`); shapes reach far past its box for other screen shapes. The sky is the play area's CSS gradient.
- The stage card holds the stage label with its progress bar and the goal (the stage's last cat as a small icon). The bar shows the biggest cat in the jar against the goal (`run.progress`: its size − 1 out of 10), updated on drops, merges and pops. At an expansion's reveal the label switches to the new stage with a short glow, the goal to the new last cat, and the bar resets without sliding backwards; at stage 5 the bar is gold.
- Banners (`ui/banners/banner.ts`): "The shrine grows!" at a stage clear that grows the jar ("Stage clear!" at the last stage) and "New cats unlocked!" with "Next goal" and the new last cat's icon at the reveal, centred 15% of the jar's height below its rim (`GameView.jarBox()`). That part of the grown jar is still empty, and the dropper above the rim stays visible. Each banner runs one CSS animation for its whole life and removes itself when it ends; while the run is paused its animation is paused too. A first-run hint is hidden while a banner shows, and reduced motion fades banners instead of popping them.
- Back in the game: the screen manager keeps one history layer while the game is open. Back opens the pause overlay and re-opens the layer; back on the pause or Game Over overlay goes to the menu (`ui/screenManager.ts`, `session.ts`).
- Use `env(safe-area-inset-*)`, `100dvh`, and `resize` / `visualViewport` listeners.
- Touch targets are at least 48 px, with pressed states and no hover-only interactions.
- Payouts on screen (GAME_DESIGN §12): every merge, Jackpot and popping cat shows a gold "+coins" in the scene (`MergeFx`; a golden merge's is `GOLDEN_TEXT_SCALE` (1.35×) bigger with a gold spark burst, a Jackpot's `JACKPOT_TEXT_SCALE` (1.7×) with a bigger burst). Where it appears and what paid (`PayoutKind`: plain, golden or jackpot) is reported through `GameView.onCoins(x, y, kind)` in CSS pixels of the play area (the camera's `worldToView` divided by the render resolution); for cash-out and Lucky Save pops that is when each staggered pop goes off.
- Coin fly (`ui/fx/coinFly.ts`): a pooled DOM coin (24 at most in the air) bows sideways from there to the HUD counter with the Web Animations API, 620 ms; a golden merge sends 3 (`GOLDEN_COIN_FLIGHTS`) and a Jackpot a shower of 8, from a ring around the origin. The counter bumps as each one lands. The coins are already in the wallet, so a flight that doesn't fit the pool is skipped, and reduced motion sends one coin at most.
- Combo (`BannerView.combo`): one persistent "Combo ×N" label from N = 2, 30% of the jar's height below the rim, text only so cats stay visible. It pops at each step, shows the Combo Charm bonus as a chip ("+16%") when there is one, and fades when the combo window passes. Jackpot ("Jackpot!" + coins, gold) and Lucky Save ("Lucky Save!", "1 left" while saves remain) use the big banner.
- Golden merges (GAME_DESIGN §5): `RunController` rolls every merge and Jackpot on its own `Rng`, seeded from the run seed with a fixed salt, so the drop queue's sequence never depends on how often cats merge or on the Golden Merge level. `merged` / `jackpot` events carry `golden`; the feedback adds a chime. Golden cats and their glint are gone (v0.12).
- Game Over: score, best, stage, the biggest cat made this run (as an icon), coins earned, a "New best!" badge for the score and "New" chips on the stage and biggest cat when they set a record.
- Menu: the UPGRADES dot shows when `anyAffordable(levels, coins)`; best score and best stage are two labelled chips under the title.
- Settings (`ui/panels/settingsPanel.ts`): a card over the menu with a back layer like the shop's. Each switch is a `<button role="switch">` row with `aria-checked`, ON/OFF in words and a knob. Haptics hides where `navigator.vibrate` is missing. "How to play" calls `Profile.resetHints()`. Reduce motion goes to `platform/motion.ts` (`setReduceMotion`): `reducedMotion()` is the setting or the OS preference, read live, and it keeps the `reduce-motion` class on `<html>` in sync. CSS keys every reduced-motion rule on that class: transitions snap, decorative animations stop, banners keep their lifetime animation as a fade.
- Shop (`ui/panels/shopPanel.ts`): a bottom sheet in `#overlays` that slides up over the menu, with a header (title, balance, close) and a scrolling list (`data-scrollable`) of 5 cards built once and repainted from `core/shop.ts` (`shopCard`: level, price state `affordable | insufficient | max`, the "current → next" value). A purchase goes through `Profile.buy(id)`, then the menu and the shop repaint, the card pulses and the balance counts down over `SHOP_BALANCE_COUNT_MS`. Opening pushes a back layer (`BackStack`), so the back button closes the shop; closing from the UI releases it. Upgrades bought apply from the next run.
- DOM cat icons (`ui/catIcon.ts`: the HUD preview and goal, banners, Game Over) are the look's sprite as an `<img>` with the cat art (no number; `data-tier` holds the tier). With `?skin=vector` they are inline SVG built from the same `config/catArt.ts` shapes as the textures (cached per look), with the tier number as text on the plate (bigger than on the sprite, at least 9 px, outlined in the plate's colour). With `?skin=placeholder` they are CSS circles with a number.

## 8. Persistence

- In play the save lives in a `Profile` (`core/profile.ts`, headless, clock injected): the wallet, upgrades, records, stats, settings and hint flags. `run/profileRun.ts` starts each run with the profile's upgrades and `bank`s every payout into the wallet before its event fires; merges, Jackpots, score and stage update the stats and records while the run plays, so a crash keeps a best score too. `runsPlayed` counts at the run start. Game Over badges compare against the records saved when the run started (`newRecords`).
- Boot: `openStorage()` (probe write, memory fallback) → `SaveStore.load()` (a corrupt, repaired or newer save logs one warning) → `Profile`; `navigator.storage.persist()` once when storage works.
- The `localStorage` key `maneki-merge:save` holds `{ version, data }` (schema v4: wallet, upgrades, records, stats, settings (sound, haptics, reduceMotion; reduceMotion was added in v0.11 without a migration, a missing field takes its default), flags; v1 → v2 drops Quick Growth and refunds its levels; v2 → v3 refunds Shrine Expansion and Fortune Teller, moves Golden Touch to Golden Merge and caps a record tier at 51; v3 → v4 caps it at 46, GAME_DESIGN §11). `core/save.ts` provides `defaultSave()`, `decodeSave()` / `migrate()`, `sanitize()` and a `SaveStore` (`load()`, `save()`) behind a `StorageAdapter`. Implementations: `WebStorageAdapter` (wraps the localStorage that `platform/storage.ts` hands in after a probe write) and `MemoryStorage` (tests, the simulator, and browsers that block storage).
- Migrations: `MIGRATIONS[n]` turns version n data into version n + 1; they run in order up to `SAVE_VERSION`. A migrated save is rewritten in the new format right away.
- Repair: every known field is validated. Counts may exceed 2^53 (stage-5 scores do), so their limit is the largest finite number. A missing field silently takes its default, so adding a field needs no migration. An invalid field (wrong type, negative, above an upgrade's max level, …) takes its default or the nearest valid value and is reported. Unknown fields are dropped.
- Corrupt data (unreadable JSON, no version, a failed migration) and repaired saves: keep a copy of the raw text under `maneki-merge:save:corrupt:<timestamp>` (only the newest 3), then rewrite the save in clean form. A save from a newer app version is backed up the same way and loaded with the fields this version knows.
- Storage errors never crash the game: a failed read starts from defaults in memory, and `save()` returns false when a write fails (storage full or blocked).
- Write on:
  - purchase (`Profile.buy`: written at once, even inside the throttle window)
  - any change (coins, records, stats, settings, hints), throttled: the first change after a quiet second is written at once, later ones at most once per second (`SAVE_THROTTLE_MS`)
  - run end (game over, leaving to the menu)
  - `visibilitychange` (hidden) and `pagehide` (`Profile.flush()`)
- A refused write keeps the changes pending and is retried with the next change or flush. A hard kill without a page hide can lose at most the last second of changes.
- Call `navigator.storage.persist()` once (best effort).

## 10. Mobile platform checklist

- `viewport-fit=cover`; no pinch or double-tap zoom (`touch-action: none` on the play area, block `gesturestart`); no text selection or long-press callout; `overscroll-behavior: none`; a fixed body so there's no rubber-band scrolling.
- Landscape on a phone shows a full-screen "Please rotate your device" overlay and pauses the run. "Phone" means a coarse pointer and a landscape viewport at most 540 px tall, so tablets in landscape stay playable.
- Audio (`audio/index.ts`): the AudioContext is created inside the first gesture (`pointerdown`, `pointerup`, `touchend`, `keydown`, captured on window) and resumed on every later gesture until it runs, with a one-sample silent buffer so iOS starts output; it is never created outside a gesture (`navigator.userActivation`), so no autoplay warning. iOS mutes web audio when the silent switch is on, which is acceptable.
- Mixer: each sound → its own gain (`config/audio.ts`) → master gain → a DynamicsCompressor used as a limiter → output. `VoiceThrottle` skips a sound started less than its `minIntervalMs` ago or with `maxVoices` still playing, and caps all voices at `MAX_VOICES`, so ten merges in one step play a pop or two, never a stack. Sound off suspends the context.
- Backgrounding: pause the run, save, and suspend audio; becoming visible resumes it (iOS may wait for the next tap).
- Android back button: history-state handling (game → pause → menu).
- WebGL context loss: recover by regenerating textures, without crashing.
- Haptics (`platform/haptics.ts`): use `navigator.vibrate` when it's available and enabled, with the patterns in `config/platform.ts`; merge ticks are rate-limited; turning haptics off cancels a running pattern; nothing on iOS (no API).
- Install hints: on an iOS browser outside standalone mode, show Share → Add to Home Screen. On Android, use `beforeinstallprompt`.

## 12. CI/CD

- Development happens directly on `main` (no side branches or PRs), so `deploy.yml`'s checks are the gate before every deploy.

## 13. Performance budgets

- 60 fps on mid-range phones (e.g. iPhone 11, Pixel 6a) with 150 cats; physics at most 4 ms per frame; no GC spikes.
- Gzipped JS under 800 KB; first load under 3 s on 4G; instant offline start afterwards.
- Final art: a WebP atlas, at most 4096×4096 in total (2048×2048 pages preferred).

## 14. Final art pipeline (M13)

- Input: `art-source/` (GAME_DESIGN §13.3); the prompts, file names and checklist are in docs/ART_ASSETS.md.
- `tools/build-art.ts` (`npm run art`, Node with sharp), for `art-source/cats/size-01` … `size-09` (PNG, JPEG or WebP):
  1. Removes the plain white background: the near-white region connected to the border becomes transparent, and the outline's anti-aliased edge is un-blended from white, so no white fringe shows.
  2. Fits the body circle (least squares) to the outline below the ears, dropping outliers.
  3. Crops a square centred on that circle, wide enough for the ears.
  4. Writes `public/assets/cats/look-NN.webp` (about 60–80 KB each) and `src/config/catSpriteData.ts` (each sprite's side, the circle's radius and the body colour, sampled from the sides of the body).
- Output is committed and precached by the service worker (`webp` is in the Workbox glob). Run the tool again after replacing a source image.
