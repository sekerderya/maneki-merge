# Maneki Merge: Technical Spec

## 1. Platforms and distribution

| Target       | How players install it                                                                                                                             | Notes                                                                                                                                                                                                    |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| iOS / iPadOS | Safari (or any iOS browser) → Share → **Add to Home Screen**. It opens full screen from its own icon and works offline.                            | No App Store, Apple developer account, Mac, or re-signing every 7 days. Home-screen web apps keep their storage. No Vibration API. Orientation lock isn't honoured, so a rotate overlay is used instead. |
| Android      | Chrome → **Install app**, which puts a WebAPK in the app drawer; or the **Google Play** app (v0.43, §16), a Trusted Web Activity of the same site. | Vibration works, and so does the manifest's orientation lock.                                                                                                                                            |
| Desktop      | Any modern browser                                                                                                                                 | For development and testing.                                                                                                                                                                             |

Why a PWA: the owner builds on Windows and won't publish to the App Store. Native iOS builds need macOS and Xcode, and apps sideloaded with a free Apple ID expire after 7 days. A PWA installs on both platforms from one URL, updates itself, and runs fully offline.

Hosting: GitHub Pages from the public repo `sekerderya/maneki-merge`. It's free and served over HTTPS, which service workers require. Live URL: https://sekerderya.github.io/maneki-merge/

Dependency rules, enforced with ESLint `no-restricted-imports`:

- `config` imports nothing except types (`import type` from `core`).
- `core` may import `config`. `physics` may import `config` and `core`. `run` may import `config`, `core` and `physics`.
- `config`, `core`, `physics` and `run` never import Phaser, DOM-only code, `game`, `ui`, `audio`, `platform` or `debug`. They must run in Node. They can't use browser globals (`window`, `document`, `navigator`, `localStorage`, `fetch`, …) or `Math.random`.
- Only `physics` (and `run` through it) imports matter-js.
- `tests/unit/layers.test.ts` lints snippets inside each layer to prove ESLint really blocks all of the above.

Randomness: `core/rng.ts` is sfc32 seeded through splitmix32. Its state is four unsigned 32-bit integers (`state()` / `Rng.fromState()`), and a unit test pins the sequence for one seed, so changing it is always deliberate. The caller picks the seed (`?seed=`, or a time-based one from the presentation layer).

- `game` and `ui` talk to each other only through the typed event bus (`core/events.ts`) and the RunController API, never by reaching into each other.

Data flow: pointer input (game) → `RunController.drop(x)` → PhysicsWorld steps → merge events → economy (score, coins) → wallet (`bank`, before the event) → event bus → HUD, FX, audio, haptics, records.

## 4. World, coordinates and camera

- The origin is the centre of the jar floor and y grows downward, so the rim is at `y = −H`. The jar is 600 × 870 world units at every stage: when the jar grows on screen, the next stage plays in the same world jar, emptied (below), so physics, gravity, speed limits, effects and line widths are the same at every stage.
- Jar geometry comes from `config/stages.ts` through `physics/geometry.ts` (`jarGeometry(stage)`: size, `rimY = −H`, dropper band, `dropY`), which the scene uses too. Walls are thick static rectangles (at least 300 units) so nothing can tunnel out. They rise `WALL_HEIGHT_FACTOR` (4) jar heights above the floor; only the part up to the rim is drawn, and the invisible rest keeps a pile that grows past the rim from spilling over. They never move.
- A cat's radius comes from its size at the current stage (`catRadius(tier, stage)` = `sizeRadius(tier − firstTier + 1)`, GAME_DESIGN §4). The physics world tracks each cat's size; `RunController.radiusOf(tier)` gives it to the scene (dropper, aim guide, pops).
- The dropper band above the rim is `0.44 × W` (`DROPPER_HEADROOM_RATIO`; 0.18 until v0.19.3, when size 4 grew to 57 and no longer fit; 0.2 until v0.21.1; 0.4 until v0.24, when size 4 grew to 69), and a dropped cat starts at its middle, `dropY = −(H + 0.22 W)`, so the biggest dropped cat (size 4) hangs clear of the jar art's top rail (`JAR_ART.railTop`, measured by `npm run art`, 56 units above the rim; a unit test keeps 2–20 units between them). The higher start lengthens every fall a little; the drop to the empty floor still took about 1 s, gravity unchanged (0.88 s since v0.41's stronger gravity, unit-tested). The drop x is clamped so the whole cat is inside the walls.
- The screen is split into bands: HUD (safe-area top + about 72 CSS px), the play band, and the safe-area bottom.
- Camera fit (`game/cameraFit.ts`): show [jar W + 2 × side margin] × [jar H + dropper headroom (0.44 W) + floor margin] inside the play band, letterboxed. Since v0.14 the canvas fills the whole screen and the DOM HUD floats over its top; the play band is the canvas below the HUD (`insetTop`: the HUD's bottom, measured by the game screen and re-read whenever the HUD resizes). The side margin is 0.19 W per side (the jar art's bamboo frame, whose top rail reaches 0.18 W past the walls, and the garden beside it: a 283 px jar on a 390 px phone; 0.15 W and 300 px before v0.17) and the floor margin 0.2 W (the feet and the rug) (`config/view.ts`). When the band is taller than that, `CAMERA_SPARE_BELOW_RATIO` (0.5) of the spare height goes below the floor and the rest above the dropper, counting the dropper band past `CAMERA_SHARED_HEADROOM_RATIO` (0.2 W) as spare above while there is that much spare, so raising the dropper in v0.21.1 left the jar where it was on a phone: on a 390 × 844 iPhone with the HUD down to 173 px the rim sits at 304 px and the floor at 713 px (unit-tested; 301 and 711 with v0.19.2's 0.18 W band, 287 and 722 in the owner's v0.14 screen). Frames of the same shape get the same spare in pixels, so the floor never moves on screen while the jar grows. `GameView.onJarBox` reports the stage jar's box in CSS pixels whenever it moves; the garden behind the canvas follows it.
- **Stage clears** (GAME_DESIGN §7). Making the stage's last cat (size 9, from two 8s) clears the stage; every 5 stages the jar grows into the next one, a look only: the camera and the jar stay still (v0.33.3; until then the camera pulled back by 4.8 while the drawn walls slid out and the rim rose), and the DOM's growth clouds and backgrounds show it. At the reveal `PhysicsWorld.setStage(next)` (which requires an empty jar) switches to the next stage: the jar is the same 600 × 870 jar. On screen nothing jumps, because nothing is in the jar. Until v0.24 the last cat (size 10) was carried over: the world shrank by 1 / STAGE_ZOOM = r(1) / r(10) (`Ball.rescale`, gone) and it became the next stage's size 1.
- The RunController owns the expansion timeline (the phase names stay those of the old zoom, so saved runs still read).
  - `run.expansion` is `{ from, to, grows, elapsedMs, progress (0–1 over EXPANSION_DURATION_MS, 5.55 s), zoomProgress (0–1 over EXPANSION_ZOOM_MS), phase }`, or null outside an expansion. It counts fixed ticks, like everything else in the run.
  - Stage clear (the tick the last cat is made, after the merge's own events): every other cat pops into its value (`catPopped { id, … }`, reason `cashOut`, oldest first, then `runCoinsChanged`), `stageCleared { stage, tier, grows }` fires, `DropQueue.newStage()` starts the stage's drop count again and turns a queued magnet into a cat of the pool's smallest tier, and the state becomes `expanding` with phase `clear` (every stage is open since v0.12, and stages have no end since v0.33: `to` is always `from + 1`). The jar grows only when `from` is a multiple of JAR_GROWTH_STAGES (5, `clearGrowsJar`); after the other clears the picks are followed at once by the reveal's work (`expansionRevealed`, then `expansionFinished`), with no zoom. A saved clear of the old last stage (`to === from`, before v0.33) is read as `from → from + 1`.
  - Phase `clear` (EXPANSION_CLEAR_MS, 1.5 s since v0.33.5): no input; physics keeps stepping (merges aren't resolved, the danger timer is reset) so the last cat finishes growing and settles alone while it shines (`game/fx/LastCatFx.ts`: a halo and a turning sunburst, canvas textures in the glow layer behind the cats, and sparkles from `SparkFx`; it follows the cat by id from `stageCleared` and bursts when the cat is gone). The combo window (1 s) runs out meanwhile. Play time advances. At its end the last cat pops (`catPopped`, reason `cashOut`) and physics pauses; without growth the picks come now, then the reveal's work and `expansionFinished`. When the jar grows the phase goes on, frozen, for EXPANSION_HOLD_MS (0.5 s): the zoom starts at EXPANSION_ZOOM_START_MS (2 s), as "Stage clear!" has slid away.
  - Phase `zoom` (EXPANSION_ZOOM_MS, 2.05 s, the growth clouds' length): `expansionStarted { from, to }` fires and the physics world pauses (time stop): play time, the drop cooldown and the combo window freeze.
  - Phase `reveal` (EXPANSION_REVEAL_MS, 1.5 s, the new place alone before the doors): the world moves into the new stage with an empty jar, the drop queue moves to the new pool (each queued cat keeps its size), and `expansionRevealed { stage, newTiers }` fires (`newTiers`: the tiers the stage adds, up to its last cat). Physics stays paused. At its end the grown jar's picks come (state `choosing`, phase `reveal`), then `expansionFinished` (v0.33.2; until then the picks came before the zoom). A saved zoom or reveal timed by the old order (its steps before EXPANSION_ZOOM_START_MS) is moved on by the hold, its picks made.
  - End: physics resumes, the danger timer resets again, `expansionFinished { stage, newTiers }` fires, and `dropReady` announces the dropper's cat. A debug jump (`jumpToStage`) clears the next stage right away, one stage at a time.
  - `instantExpansion` (tests) runs the whole sequence inside one tick.
  - While the danger timer runs, `dangerTick { secondsLeft }` fires each time the countdown reaches a new whole second (3, 2, 1), for the tick sound and the countdown pulse.
  - While the run is paused (backgrounding, rotation, the pause button) the timeline stands still with it and continues from the same tick.
- **Expansion visuals.** The canvas draws the jar still; from v0.15 to v0.33.2 `game/expansionView.ts` zoomed the camera from the tick timeline (gone with `growFrame`, `STAGE_ZOOM` and `EXPANSION_WALL_LAG`). The growth is the DOM's (`ui/fx/growthClouds.ts`, started by the session on `expansionStarted`): about forty `<img>` clouds over the play area (z-index 1: over the canvas and the garden, under the hint, the banners and the HUD), placed by `ui/fx/cloudLayout.ts` (pure, fixed seed, unit-tested to cover phones and tablets without a gap), each running one Web Animation (transform and opacity only) for the whole 2.05 s; a cream wash under them hides any gap while they cover the screen. A zero-length animation on the layer fires at full cover, when `gameScreen.setJar` swaps the background and plays its settle (scale 1.15 → 1 around the jar's feet). Being Web Animations, they pause with the run (`scenery.setPaused`); a restored run gets its background at `expansionFinished`, without clouds. The old zoom's notes:
  - Zoom progress `t = (elapsedMs − EXPANSION_CLEAR_MS + alpha × PHYSICS_STEP_MS) / EXPANSION_ZOOM_MS` during the zoom (0 during the clear, 1 at the reveal). `renderAlpha` is the fraction of a tick the frame's leftover time has reached (`FixedStepper.alpha`), so the zoom moves smoothly at 60, 90 or 120 Hz and through rAF jitter instead of stepping in whole ticks. It only affects rendering.
  - The camera fits the jar grown by `STAGE_ZOOM^easeInOut(t)` (`growFrame`): the frame grows by a constant ratio per moment, which looks like an even zoom even across a nearly fivefold change. The drawn walls and rim use `STAGE_ZOOM^wallProgress(t)` with `wallProgress = easeInOut((t − EXPANSION_WALL_LAG) / (1 − EXPANSION_WALL_LAG))` and a lag of 0.25: the view pulls back first, then the walls slide outward and the rim rises into the new frame. The jar always stays inside the camera frame, both arrive together when the zoom ends, and the floor never moves on screen (unit-tested). A lag of 0 locks the jar to the frame.
  - The physics walls never move; nothing moves during the zoom (time is stopped), and at the reveal the jar is empty (headless test: nothing escapes, launches or jumps through four stage clears under a pile).
  - The stage clear's pops show each popped cat's own sprite (`BallRenderer.detach`) growing and fading with a ring and a gold "+coins" (`PopFx`); pops of one tick go off from the top of the jar down (by y), 45 ms apart, within 900 ms in all (v0.33.5), so a clear ripples down the jar while its last cat shines. The zoom start bursts gold sparks along the rim (`SparkFx`, one pooled Phaser emitter, paused with the run), and so does the reveal.
- Resize or rotation re-fits the camera immediately, without a tween, also in the middle of an expansion: the frame is recomputed from the timeline every frame.

## 5. Physics

- matter-js engine with a fixed timestep of 1/120 s and an accumulator (at most 5 substeps per frame). Physics never depends on frame rate.
- **Exact circle contacts** (`physics/circleCollision.ts`). Stock matter-js treats every body as a polygon and runs SAT on its vertices: with 150 cats SAT took 55–65% of a step, and polygon cats roll over facets (a 20-gon won't roll on slopes under ~9°). `installCircleCollisions()` wraps `Matter.Collision.collides` once: a cat–cat pair uses an analytic circle test and a cat–wall pair a circle-vs-axis-aligned-box test, each with one contact point midway through the overlap; every other pair keeps SAT. A cat's body is still a polygon (12 sides drawn around the circle) because matter-js needs vertices for its broadphase bounds, but its mass and inertia are set from the true circle. The returned record follows matter-js 0.20.0's internal contract (record reuse through the pairs table, `bodyA` = smaller id, normal from bodyB to bodyA, one persistent support point so warm-starting carries over), so matter-js is pinned to exactly `0.20.0`, and tests check the contract and agreement with SAT before any upgrade.
- **Coulomb friction** (`physics/friction.ts`, v0.23.7; owner: the cats "slide over each other like on ice instead of rolling"). matter-js 0.20.0's friction fails for discs in two ways. While two bodies slip, it removes a fixed amount of slip per iteration (`friction × timeScale³`), whatever presses them together. And it sizes the impulse that should stop a slip with the effective mass along the normal, which leaves out rotation, so for a cat it overshoots: with inertia × 2 it reversed the slip exactly, and the 8 iterations flipped it back and forth. Raising the friction to 0.5 only raised the rolling share of cat–cat contacts in play from about a third to about half. `installCoulombFriction()` replaces `Resolver.solveVelocity` once with a copy of matter-js's (MIT) whose friction is Coulomb's, as in Box2D: each iteration adds the impulse that stops the slip, sized with the effective mass along the tangent (mass and inertia), and the step's total stays within μ times the contact's accumulated normal impulse (`CAT_FRICTION` between two cats, `JAR_FRICTION` against the jar). matter-js keeps normal impulse only at a resting contact and clears it on an impact (approaching faster than 120 u/s), so an impact carries no friction and a landing cat shoves as before; with friction on impacts too, a size-3 dropped on a size-5's shoulder moved it 10 units instead of 188. The normal impulses are matter-js's own: a straight stack, where nothing slips, matches matter-js bit for bit (unit-tested). Like the circle contacts, it relies on the pinned matter-js 0.20.0.

  The owner chose μ 0.8 with a real disc's inertia from three measured options (μ 0.5; μ 0.8; μ 0.8 with inertia × 1): it rolls almost always and keeps the shoves. With inertia × 1, matter-js's friction against the jar overshot further and made resting cats shiver (up to 5 rad/s), so the jar got Coulomb friction too. Measured headless against v0.23.6 (bot: drops as fast as it can at random x, 16 seeds, contacts over its first 60 s):

- **Drawn between steps (v0.41).** Physics runs in fixed ticks of `PHYSICS_STEP_MS`, so a frame covers 0 to 3 of them (at 60 Hz mostly 2, at 90 Hz 1-1-2, at 120 Hz 0-1-2 with jitter). Until v0.41 the balls were drawn where the latest tick left them, so a falling cat moved unevenly from frame to frame (up to about 13 units at 60 and 120 Hz) and the owner felt a low frame rate. Now the run calls `world.holdPoses()` at the start of every tick (and on resume), which stores each ball's position and angle as `fromX`, `fromY`, `fromAngle` (BallView, rendering only; a new or restored ball starts from where it is), and the scene draws every ball and what follows it (cracks, glows, numbers, Heavy Drop's trail, the last cat's halo, kintsugi, the curse, the magnet's ring) `renderAlpha` of the way from there to its pose now (`game/drawnPose.ts`). That costs at most one tick (8.3 ms) of display lag and changes nothing in the simulation, saves or hashes. Measured in Chromium on the GPU at 60 Hz: the drawn fall's speed jumped by up to 85% from one frame to the next, now up to 30% (rAF timing noise). `?interp=0` draws the latest poses, to compare on a phone.
- Timers count whole steps (`stepsFor(ms)`): 2.5 s is exactly 300 steps, so floating-point noise never moves a deadline. `FixedStepper` divides the accumulated time by the step instead of subtracting step by step, for the same reason.
- Density per size is `0.001 × r(1) / r(s)`, so mass grows like r instead of r². This limits mass ratios: the last cat is 4 times as heavy as the first, not 16 times.
- **Square corners** (v0.23.4, GAME_DESIGN §6). The floor is a plain box under the walls, like the walls themselves. From v0.14 to v0.23.3 the floor carried rounded corners (`plugin.roundedFloor`, quarter circles of radius 112, then 168) tested analytically in `circleCollision.ts`, and a dropped cat whose first touch was a curve got a half-second "first-landing cushion" (`CORNER_CUSHION_MS`), because a curve turned its fall sideways and swung it across the jar. The owner's square bamboo frame removed the curves, and with them the cushion and the curve parts of the rug below: a cat dropped against a wall now lands dead in the corner and stays there.
- **No rug** (v0.23.6, the owner's call). From v0.19.4 to v0.23.5 a cat touching the floor and no other cat lost 800 u/s of speed every second (`FLOOR_ROLLING_RESISTANCE`, `PhysicsWorld.rollOnRug`) and was made to roll (v0.19.5); it came with the curved corners. Now the floor holds a cat like the walls do: friction gets a pushed cat rolling, and air friction alone slows it, so a size-2 cat pushed at 300 u/s rolls within 0.12 s, still rolls at about 110 u/s a second later, about 155 units on, and glides about 330 units in 7 s if nothing stops it (measured headless; v0.23.6: 80 u/s, 120 and 250 units; the rug stopped it after 48 units in 0.33 s). A merged size-3 born turning on the empty floor drifts about 45 units.
- **Bounce per body** (`physics/restitution.ts`). matter-js gives a pair the larger restitution of its two bodies, so a bouncy cat would bounce off the floor as much as off another cat. `installRestitutionOverride()` wraps `Matter.Pair.update` once (matter-js 0.20.0 sets `pair.restitution` there on every step a pair is active, and `Pairs.update` looks the function up on each call): a body that carries `plugin.restitution` forces that value on its pairs. Only the floor does, with 0. A cat landing on a cat that rests on the floor hardly bounces either, because the floor absorbs the push.
- The v0.13 retune, measured headless against v0.12 (with v0.12 also on the dead floor where noted): a size-2 cat rolling at 600 u/s into a resting size-6 moves it 47 units instead of 21; a size-2 dropped into a 20-unit gap between two size-3s pushes them 397 units apart instead of 109 (71 on a dead floor); a size-3 dropped on a size-5's shoulder shoves it 170 units instead of 47. Most of it comes from the faster fall; the friction, inertia and mass changes roughly double it again. The cost is in the 150-cat stress pile: it gets under 75 u/s after 7–9.5 s instead of 3–4.5 s, its largest overlap is 8–13% instead of 4–5%, and a step takes 0.93 ms instead of 0.78. In play (a bot dropping every 0.75 s for up to 4 minutes, 4 seeds) cats that landed more than 3 s ago move at 2 u/s on average, as before, and none faster than 60 u/s.
- The v0.12 retune was measured headless against M4's values: a size-2 cat rolling into a size-6 one moves it 69 units instead of 48 (+45%), a size-2 cat dropped into a gap between two size-3s pushes them 243 units apart instead of 202 (+20%), a 60-cat pile still settles in about 4 s, and the stress, growth and chaos tests pass unchanged. The chaos runs also showed (with both the old and the new values, about once in 300 000 ticks) a light cat squeezed against a wall by a newly merged neighbour poking its centre a few units into the wall for one step, because matter-js only finds the wall contact on the next step; the chaos test allows exactly that (one tick, under half a radius).
- Gravity and the speed limits are the same at every stage: every stage plays in the same world jar (§4) instead of a grown one. A grown world would break matter-js: its resting-contact threshold is an absolute speed, so stacks would turn jittery from stage 3 on.
- Merges (`physics/merges.ts`, run after every step):
  - The step makes one pass over matter-js's pair list, which with sleeping off holds exactly the pairs that overlap this step (`collisionStart` + `collisionActive`), once each. It records each cat's first contact and collects same-tier cat pairs.
  - Order: candidate pairs are sorted by (older cat id, younger cat id), so the oldest cats merge first. Our ids come from creation order, so the order never depends on matter-js internals.
  - One merge per cat per step: a pair with an already used cat is skipped. Three touching cats give one merge; the third can merge on a later step. New cats aren't in this step's pairs, so chains continue on the next step at the earliest.
  - Two of the stage's last cat (or bigger) make a Jackpot and vanish. Otherwise the new cat is born at rest exactly at the midpoint (v0.13; until then it took the parents' average velocity, capped at 400 u/s, and drifted off the midpoint), at the parents' size, and grows linearly into its own radius over `MERGE_GROW_MS` (120 ms, 15 steps). It inherits the earlier landing time, so a pile over the line keeps counting.
  - It starts to turn, as if another cat had clipped it (v0.13): its rim moves at `MERGE_SPIN_RIM_SPEED` (80 u/s), so a size-2 cat turns at 2.4 rad/s and a size-11 at 0.4 rad/s, and friction and air friction slow it down within a second or so; on the floor it rolls a short way. The direction (`mergeSpinDirection`) comes from how the parents met: two cats sliding past each other drag each other's rims and both turn the same way, so the new cat turns that way (a cat landing on the right shoulder of another turns clockwise). When they slide past each other slower than `MERGE_SPIN_MIN_SLIDE` (20 u/s), the parents' own turning decides, and if they don't turn, the parity of their ids.
- Growth without launches: linear growth has the lowest peak growth rate (about 1.5% of the radius per step). matter-js 0.20 removes overlap in its position solver by moving `position` and `positionPrev` together, so growth pushes neighbours without giving them velocity. On top of that, every cat touching a growing cat is capped at `GROWTH_NEIGHBOUR_MAX_SPEED_BASE`, and every cat on every step at `MAX_SPEED_BASE` and `MAX_ANGULAR_SPEED`. A test wedges a big pair between the walls under a settled pile and resolves every merge at once: upward speeds stay under 20% of the speed limit.
- **Batch 18's merge rules** (`MergeResolver.resolve(world, cap, rules)`, GAME_DESIGN §15.10–§15.11):
  - **Hubris** (`threesUpTo` 5): the step's same-tier contacts between cats up to size 5 become a touch graph (shard mates' contacts left out); every other contact (bigger cats, jokers) stays a pair. The balls in any contact are gone through by id, oldest first; each still-free ball takes its oldest merge among free balls, by the sorted ids of its other balls: its oldest pair partner (a joker's merge with a cat below the cap, or a bigger cat of its tier) or its oldest connected three (itself and two of its neighbours, or a path through one neighbour); failing both, its oldest small neighbour it has touched for `pairWaitSteps` (`HUBRIS_PAIR_WAIT_MS`, 0.5 s). The resolver keeps each small pair's wait (the step it started touching and the step it was last seen); a pair not seen for `pairGraceSteps` (`HUBRIS_TOUCH_GRACE_MS`, 0.1 s: two resting cats' contact flickers from step to step, and without the grace the waits kept starting over and the bot measured 1 clear in 30 instead of 3) or whose cat is gone is forgotten. The waits are part of the run's state: hashed and saved (`hubrisWaits`). Every older ball is used or can't merge at that point, so the ball is the oldest of whatever merge it makes, and without Hubris this is exactly the pair order above (that path is kept as it was; `tests/physics/legacy.test.ts` pins a v0.33.5 seed's play). A three's cat is born at the centroid at the biggest radius, `HUBRIS_SIZE_STEP` (2) sizes up, one more with a golden cat (never above the cap), turning the way its two oldest cats slid; `MergeOutcome.parts` is 3 and the economy pays it `THREE_WAY_PAYOUT` (1.5) times a pair.
  - **Porcelain** (`porcelain`): after the merges, `resolver.cracks` lists every cat (by id) once per merge (in resolution order) whose balls reach it within `PORCELAIN_REACH` (15), except the merging size, the cap, boulders, hanabi, jokers and the step's new cats. The run rolls each entry on its own generator: an intact cat is cracked, a cracked one breaks into two of the size below at `pieceSpots` (x ± r', moved together inside the walls, `physics/spawns.ts`), each a **shard mate** of the other (`Ball.mate`: the other piece's id); a pair or a three with both mates is skipped. At the start of each `resolve` the mates part (both `mate` null) once both have grown in and more than `PORCELAIN_MATE_GAP` (10) lies between their edges, or once the world step reaches their `mateUntil` (the break's step plus `PORCELAIN_MATE_MS`, 1 s, v0.35.2), and a piece whose mate is gone forgets it; the rest is saved state as before. A cracked cat's merge sets `MergeOutcome.cracked` (the kintsugi flash).
  - **Echo:** the run, not the resolver, adds an echo cat after a merge's events (`echoSpot`: level with the new cat at x ± (r_new + r_echo) on a seeded side, the other side if that hits a wall, else straight above), with the new cat's landing time, for merges of sizes 5–7, and only the first after each drop (`echoUsed`, cleared by `drop`; saved and hashed).
  - Echo cats and a broken cat's pieces start at `SPAWN_START_RADIUS_SHARE` (a quarter) of their radius and grow like merged cats, so the growth cap and the position solver push their neighbours aside without launching them.
- **Batch 19's rules** (GAME_DESIGN §15.12–§15.14):
  - **Dice** (`MergeRules.dice`, a roller the run passes in): `mergePair` (not a joker's merge or a Jackpot) and `mergeThree` work out the new cat's normal tier, and when it is below the cap call the roller once, in resolution order, before the new cat is made (`rollFor`): `lucky` makes it one tier bigger (never above the cap), `fizzle` makes it the tier that met, born at the parents' radius so it doesn't grow. The run's roller draws once per call on its own salted stream (`diceRoll` in `core/picks.ts`: < 1/6 lucky, < 2/6 fizzle). `MergeOutcome` says what the die showed (`dice`) and which balls merged (`from`, their ids); hits, cracks and the economy treat a fizzle as any merge, and `echo` skips it. Without Dice no roller is passed and nothing changes (the pinned v0.33.5 and v0.34.0 seeds play the same).
  - **Cursed Bell** lives in the run: `drop` first counts the curse down (or turns its cat to stone), then, with the stage's `dropsThisStage` at or past `curseDue` and no curse on, curses a random fitting cat (`curseRng`). A merge whose `from` holds the cursed cat lifts it and banks `CURSE_LIFT_BONUS` × its coins more (`RunEconomy.bonus`: no score, no combo); `take` lifts it with no bonus; after the step's removals (and in a Lucky Save, a debug crack and a stage clear) a curse whose cat is `removed` just ends. Turning to stone removes the cat and adds a boulder of its tier with one hit at its position, with its velocity, spin, angle (`BallSpec.angle`) and landing time. Events: `curseBegan`, `curseTicked`, `curseEnded` (`lifted`, `taken`, `gone`, `stone`, with the bonus), `catPetrified` (the cat's and the boulder's ids).
  - **Copycat** lives in the queue: `DropQueue.copyNext(tier)` turns the cat in NEXT to `tier` (not the dropper's, never a run's first two items or a special ball); the items rolled after it are the seed's own. The run calls it after a step's merges with the latest merge's tier, at most `COPYCAT_MAX_SIZE`, and emits `nextChanged` when NEXT changed. (v0.35.0's `follow` also turned every later cat to that tier until the next merge.)
- **Batch 18's falling forces** (`PhysicsWorld.setFallForces`, GAME_DESIGN §15.8–§15.9): before each step, every ball still falling (`landedMs < 0`: in play, only balls that left the paw) gets the wind's sideways acceleration (100 u/s² per Wind level, the run's direction) and Heavy Drop's extra gravity as matter-js forces, integrated in that step; a ball that has touched another ball or the floor feels neither. The wind tilts the whole fall: its push is scaled by (gravity + extra gravity) / gravity, and `RunController.drop` gives a heavy ball `PhysicsWorld.windLaunch`'s sideways speed (start speed × wind / gravity), so a heavy ball follows a plain one's slanted line (measured: the same drift within a unit at every level, full fall or 300 units). While any falling force is on, `scanContacts` doesn't count a wall contact as a first contact, and a falling ball within `WALL_TOUCH_SLOP` (1 unit) of the wall the wind blows toward gets no wind (none into the wall, none at launch), so it slides down the wall without Coulomb friction and lands as soon as in the open (before v0.34's fix, the wall ended a heavy fall: up to 71% slower). A falling ball's speed limit is `HEAVY_DROP_MAX_SPEED` (4800 u/s, 40 units per step, under a size-1 radius) while Heavy Drop is on, `MAX_SPEED_BASE` otherwise; `scanContacts` marks the first contact before the limits apply, so the step a ball lands on already caps it at `MAX_SPEED_BASE`. With every level at 0 nothing changes (the pinned v0.33.5 seed plays the same).
  - Heavy Drop's start speed and extra gravity (`HEAVY_DROP_START_SPEED`, `HEAVY_DROP_GRAVITY_BONUS`: a quarter of the base gravity per level, the start speed solved by bisection for falls of 0.66, 0.53, 0.41, 0.33 and 0.24 s) land a size-1 cat at 2000, 2339, 2789, 3327 and 4361 u/s, up to 36 units per step (v0.34 retune; first built with half the base gravity per level for 0.8 to 0.3 s).
  - **The landing knock** (`knockAside`): `pushFalling` records each falling heavy ball's speed before the step; on the step it first touches anything, every ball it touches from above (contact pointing down) gets a sideways push of `HEAVY_DROP_KICK` (0.18) × that speed × (downward share of the contact)², away from it (a dead-centre hit picks a side by the heavy ball's id parity), and the heavy ball `HEAVY_DROP_KICK_BACK` (half) of it the other way, both within the speed limit. Without it a dead-centre hit moved the cat 0 units at every level (the impulse went straight into the floor).
  - **Tunnelling guard** (`physics/fallGuard.ts`). At more than half a size-1 radius per step (`FALL_GUARD_DEPTH`, 20.5 units: what `MAX_SPEED_BASE` allows) a falling ball could start a contact deep inside a small cat. Of the two plain answers, a speed cap at 20.5 units per step can't fall in under 0.39 s (levels 4 and 5 need 0.4 and 0.3 s), and substepping the whole world while a heavy ball falls doubles the step's cost for the whole pile almost all the time from level 3 (drops come every 0.45 s) and changes how the pile is solved. So the guard is a sweep for the falling ball alone: before the step, its move as matter-js's Verlet integrator will make it (velocity × air friction plus gravity and forces) is swept against every other ball's circle, the floor and the walls; if it would travel more than the depth past its first contact, its position and previous position move back along its path together (its speed stays), so the contact starts at most 20.5 units deep and it still hits at full speed. It costs one pass over the balls per falling heavy ball and step. Walls and the floor are 300 thick, so nothing could pass through them anyway.
  - Measured headless (`tests/physics/heavyDrop.test.ts`): falls within two steps of the card's times for sizes 1 and 4; no contact deeper than 20.5; in a jar filled to the rim (45 cats), 100 drops (each taken away 0.25 s after landing, as a merge would) leave every cat in the jar and above the floor at every level. Over six seeds, ordinary drops and levels 1 and 3 push no other cat over the rim; at level 5 the knock squeezes one a little over it in 3 seeds (156–244 u/s, at most 14 units high; the test allows under 300). The heavy cat itself may bounce back over the rim of a full jar at up to about 320 u/s (ordinary: up to 32). `npm run test:perf` is unchanged (the guard and the knock run only while a heavy ball falls or lands).
- Stability acceptance test (headless): 150 random cats of a stage's drop pool settle within 10 s of simulated time (110 since v0.19.4, below). They overfill the 600 × 870 jar, so the pile rises past the rim and leans on the tall walls. After settling, no cat has escaped, the largest overlap is under 15% of the smaller radius, and no cat moves faster than the clamp. "Settled" means every cat is slower than 5% of the speed limit (120 u/s since v0.13, 75 before) from that moment on (checked until 12 s), with speeds averaged over 0.1 s since v0.14. Resting cats show velocity jitter (a cat can read 150 u/s while its position stays within a unit); the taller, curved-bottom pile of v0.14 reads such single-step spikes often enough to fail an instantaneous check on some seeds, although its cats move no more than on the flat floor (over the 2 s after 10 s, the farthest cat moves 0.02–0.57 of its radius with the curves and 0.01–0.42 without, 6 seeds). With the 0.1 s average it settles in 2.2–9.5 s (flat floor: 2.3–8.4 s). v0.19.3's bigger small cats made 150 of them a third more cat than the limits were set for: the pile reached 1.8–2.0 jar heights, and over 12 seeds 1–2 crept at its top past 10 s (at 123 u/s against the 120 bar) and several overlapped 15–20%, with the v0.19.3 and the v0.19.4 physics alike; which seeds passed was luck. Since v0.19.4 the test drops 110 cats, as much cat as 150 were before (the drop weights' mean area grew 36%): over 12 seeds they settle in 1.6–3.9 s with the largest overlap at 4–12%. The performance test keeps 150 cats. The fixture packs 5 cats per row (cells of 2 r(4) + 6; with + 12 only 4 fit and the grid reached 5.5 jar heights). Positions are checked separately, through overlap and wall penetration. With Coulomb friction (v0.23.7), 12 seeds settle in 1.6–5.1 s (1.6–4.6 s just before) with the largest overlap at 5–8% (6–14%).
- Measured in M4 (dev machine, Node 24): a step with 150 settled cats takes **0.79 ms** on average (0.70 ms in v0.10's jar, 0.93 ms with v0.13's heavier, more slippery pile; 0.93 ms with v0.19.3's bigger cats against 0.86 ms just before, on the same machine) (the Coulomb solver of v0.23.7 costs what matter-js's did: 1.06 against 1.04 ms, best of 40 interleaved runs on a busy machine) (`npm run test:perf`, budget 2 ms; stock polygon SAT took about 1.8 ms). The stress test settles in about 4–7 s, with the largest overlap at 4–8% of the smaller radius, wall and floor penetration at 2–4%, and nothing escaping. matter-js passes, so planck.js isn't needed.
- Known: tall piles keep creeping. With 150 cats, a slip of 0.1–0.4 of a radius within half a second can still happen after 10 s. It comes from matter-js's soft stacking; higher friction and more iterations didn't remove it. In play, cats arrive one at a time and merge, so piles are smaller. Watch it in the M5 phone test.
- Determinism (`tests/physics/determinism.test.ts`):
  1. One seeded RNG per run, used only by the drop queue. Physics has no randomness, and the matter-js engine never calls its own random.
  2. Fixed ticks: `update(frameMs)` only decides how many ticks run. Every timer counts ticks, never frame time or the wall clock (`Common.now` only feeds matter-js metrics).
  3. Inputs apply between ticks, so a run is its seed plus (tick, input) pairs. The test records a run driven by random frame lengths and replays it tick by tick: `stateHash()` (FNV-1a over the exact float bits of the run and every body) matches at every checkpoint, through an expansion.
  4. Ordering uses our own cat ids. matter-js body ids are global per process, so two worlds get different ids, but matter-js only compares them; the test builds another world in between to prove it.
  5. Exact replays hold on one JS engine. V8 and JavaScriptCore may differ in the last bit of `Math.sin` and `Math.cos`, so a seed isn't guaranteed to replay bit for bit across browsers.
- If matter-js can't pass the stability test after tuning, switch to planck.js behind the same `PhysicsWorld` interface and record why here.

## 6. Rendering

- Phaser 4 with WebGL (Canvas fallback): a transparent canvas over a CSS background. Phaser's sound manager is off (`audio.noAudio`, v0.42.12): the game's own engine plays every sound (§10), and Phaser's opened a second AudioContext at boot that ran, silent, from the first tap on. With the raster art the WebGL context has no multisampling (`antialiasGL: false`, v0.42.12, §13); the vector and placeholder skins keep it for their Graphics edges.
- High-DPI: the game uses `Scale.NONE`. `game/index.ts` sizes the canvas to the play band × min(devicePixelRatio, 2.5) (`MAX_RENDER_RESOLUTION`) and shows it at CSS size through the scale zoom (1 / resolution). A `ResizeObserver` re-fits it; the camera zoom is canvas pixels per world unit.
- **Adaptive resolution (v0.23.8).** A phone that stutters through play renders the canvas at fewer pixels: `game/resolutionGovernor.ts` (pure, unit-tested) watches frame times while the run is `playing` (anything else, a resize or a stall over 250 ms starts the watch over, and the first 500 ms after it are ignored) in windows of 2 s. A window is slow when frames average over 1000/45 ms and are uneven; a steady rate down to 28 fps is a cap (iOS Low Power Mode and battery savers hold 30 fps), not stutter, and fewer pixels would not lift it. A slow window steps the cap down one level (`RENDER_RESOLUTION_STEPS`: 2.5 → 2 → 1.5, skipping levels the screen is already under, so a 2× phone has 2 and 1.5). The next window must show frames at least 10% shorter, or the step is undone and the governor stops for the session: a phone held back by its CPU gets nothing from fewer pixels, so it keeps the full resolution. It never steps back up within a session. Phones that keep up never leave the full resolution. `?res=<n>` fixes the cap (0.5–2.5) and turns the governor off, to see what a slow phone gets. Measured (Chromium, 390×844 at 3×): on a GPU, the resolution stays at 2.5 throughout; on the software renderer (a stand-in for a weak GPU) play went from 28 fps at 2.5 to 40–53 at 2 and 55–61 at 1.5; with the CPU throttled 20× on a GPU it tried 2, saw no gain and went back to 2.5 for good.
- The game loop sleeps (`loop.sleep()`) while the menu is visible and wakes when a run is shown.
- The `BallSkin` interface (`game/skins/BallSkin.ts`) gives a frame per tier, an optional upright number frame for the active stage (a tier's size depends on the stage) and the cat's main colour (merge particles, the pop ring). A frame is a texture key (and the frame within it, for an atlas) plus world units per texture pixel at the radius of the cat's size; that scale includes the hit-radius ratio. A number frame also says how far below the centre the number sits (`offset`, in radii, along the cat's own down axis): `BallRenderer` and the dropper put it there, rotated with the cat, but never rotate the number itself. Implementations:
  - `ArtSkin` (the default since v0.16, GAME_DESIGN §13.1): the nine raster looks in `public/assets/cats/` (`config/catSprites.ts`, data generated by `npm run art`, §14). Boot loads and decodes them with the fonts (`loadCatArt`; if they fail or take over 8 s, the game falls back to `?skin=vector`); all ten sizes share one canvas texture (an atlas with a frame per size, packed in rows at most 2048 px wide by `game/skins/packRows.ts`: 1743 × 2035 px, about 14 MB, with the v0.23.8 cats) at `CAT_PX_PER_UNIT`, scaled so the fitted body circle plus a dark outline (`catOutlineWidth`: the silhouette, filled with the outline colour, stamped 24 times round a circle under the body) lands on the physics radius (big reductions go through halving steps). No numbers (`number()` returns null), so its textures are the same at every stage.
  - `CatSkin` (`?skin=vector`, the default in v0.11–v0.15): the nine looks of `config/catArt.ts` drawn with `Path2D` into canvas textures at `CAT_PX_PER_UNIT` (2.5). Each look is scaled so the outer edge of its outline (`bodyEdge`) lands on the physics radius; the ears poke out above it inside the texture. Numbers are drawn in the look's plate colours, with a thin outline in the plate's colour.
  - `PlaceholderSkin` (`?skin=placeholder`): circles and numbers drawn with the 2D canvas API, number offset 0.
    The canvas skins are refreshed after a WebGL context restore. `createGame(parent, skin)` picks the skin from the URL flag; the DOM icons follow it (`setIconSkin`).
- **Textures** (`game/skins/skinSets.ts`). The world has the same scale at every stage and the looks repeat with the sizes (GAME_DESIGN §13), so a size looks the same at every stage: the 10 body textures are drawn once, at 2.5 texture pixels per world unit (`CAT_PX_PER_UNIT`, `PLACEHOLDER_PX_PER_UNIT`), never upscaled on phones and tablets, and shared by every stage. Only the numbers differ per stage: each stage's set is its 10 tiers' numbers, drawn at their size's radius, the drop pool's first. Canvas textures get no mipmaps (Phaser 4.2 renders with WebGL1), so during the nearly fivefold zoom-out the old stage's textures are shrunk a lot for about a second; at the reveal everything is back at its normal size.
  - `BallSkin.prepare(stage, budgetMs)` draws the next stage's numbers during the zoom, about 4 ms per frame (physics is paused then, so it costs no frames); `setStage(stage)` switches at the reveal (finishing anything missing) and bumps `revision`, and `BallRenderer` gives live sprites their new textures. The skin keeps stage 1's numbers (every run starts there) and the previous stage's, and frees the rest. Bodies take about 11 MB of texture memory with the lucky cats, 14 MB as one atlas since v0.23.8 with its gaps and uneven rows (size 9 alone is about 910 px square, as size 10 was until v0.24; 940 before v0.19.3; 16 MB before v0.15 with size 11, 22 MB before v0.12 with size 12 and golden bodies).
  - Line widths: the jar's lines are fractions of its width (they grow with it during the zoom), and floating texts and the danger countdown render at the current zoom, so all of them keep their on-screen size and sharpness. The pop ring texture is 512 px, so a last cat's Jackpot ring isn't upscaled.
- Numbers are separate upright sprites in a layer above all bodies, so a 6 never looks like a 9.
- **Scene art (v0.17).** With the art skin, `JarView` and `PawView` draw the owner's images (`config/sceneSprites.ts`, data from `npm run art`, §14) instead of the vector art below. The jar's two images (behind and in front of the cats) become canvas textures with a frame per piece; each piece is placed by mapping the image's opening onto the physics jar (`jarArtToWorld`, about 1.08 world units per pixel across and 1.07 down), so the jar still grows with the stage. The paw is one texture; a 1 px plain row of its arm is a second frame. Since v0.25 the paw floats: the texture is cropped `PAW_ART_SHOWN - PAW_ART_FADE` (105) units above the paw's bottom and the arm row, stretched over the last `PAW_ART_FADE` (55) units, fades out with per-corner alpha (WebGL). With `?skin=vector` the arm still reaches up to the screen's top. ## 8. Persistence

- In play the save lives in a `Profile` (`core/profile.ts`, headless, clock injected): the wallet, upgrades, records, stats, settings and hint flags. `run/profileRun.ts` starts each run with the profile's upgrades and `bank`s every payout into the wallet before its event fires; merges, Jackpots, score and stage update the stats and records while the run plays, so a crash keeps a best score too. `runsPlayed` counts at the run start. Game Over badges compare against the records saved when the run started (`newRecords`).
- Boot: `openStorage()` (probe write, memory fallback) → `SaveStore.load()` (a corrupt, repaired or newer save logs one warning) → `Profile`; `navigator.storage.persist()` once when storage works.
- The `localStorage` key `maneki-merge:save` holds `{ version, data }` (schema v7: wallet, upgrades (the shop cards' levels, blessing cards included; a missing card takes its start level), records, stats, settings (sound, haptics, reduceMotion; reduceMotion was added in v0.11 without a migration, a missing field takes its default), flags; v1 → v2 drops Quick Growth and refunds its levels; v2 → v3 refunds Shrine Expansion and Fortune Teller, moves Golden Touch to Golden Merge and caps a record tier at 51; v3 → v4 caps it at 46; v4 → v5 refunds Golden Merge; v5 → v6 caps a record tier at 45; v6 → v7 (v0.36, the new economy) keeps only the settings and starts the profile over, the owner's call, GAME_DESIGN §11). A purchase also needs the card's gate: `Profile.buy` passes the best stage to `buy` (`core/upgrades.ts`), which refuses a locked card. `core/save.ts` provides `defaultSave()`, `decodeSave()` / `migrate()`, `sanitize()` and a `SaveStore` (`load()`, `save()`) behind a `StorageAdapter`. Implementations: `WebStorageAdapter` (wraps the localStorage that `platform/storage.ts` hands in after a probe write) and `MemoryStorage` (tests, the simulator, and browsers that block storage).
- `maneki-merge:scenes` (v0.44): `1` while the device shows the menu's Scenes button (GAME_DESIGN §2.6); absent otherwise. Not part of the save: it is the owner's tool, and a storage that throws only means it isn't remembered.
- The run in progress (GAME_DESIGN §11) has its own key, `maneki-merge:run`: `{ version, save: { run, recordsBefore } }` (`core/runSave.ts`, `RUN_SAVE_VERSION` 2 since v0.36: the economy changed and every profile starts over, so a run saved before it is dropped; a snapshot whose upgrades lack a card loads it at the card's start level). `RunController.snapshot()` (taken between ticks; null after game over) holds the seed, upgrade levels, the state to resume to (playing, expanding or choosing), ticks, cooldown, Lucky Saves, pick levels, the wind's direction, whether a merge has echoed since the last drop, Hubris's waiting pairs, the curse (`curse`: the cursed cat's id, the drops left and what the count started at, `total`, missing before v0.35.3; or null) and the stage's drop it is next due at (`curseDue`), offer and pick queue (`trial`, `rule` or `blessing`), the expansion timeline, the seven RNG states (the queue's, the specials', the picks', Porcelain's, Echo's, the curses' and Dice's), a lightning strike holding time still (`lightning`: the lightning ball's id, the struck balls' ids and the steps held; v0.42, missing or null when none), the queue, economy and danger timer, and the world: stage, steps, next id, paused, and per ball its kind, tier, golden, hits left, cracked, shard mate and the step it parts from it anyway (`mateUntil`, missing before v0.35.2: it parts at once) (Porcelain), radius and growth, first contact, and its matter-js body between two steps (position and previous position, angle and previous angle, velocity, spin, last step length, position-solver warm start). `RunController.restore()` rebuilds it paused and throws a RangeError when the rules can't hold it (a tier the stage doesn't have, a pick without an offer, …). matter-js's contact cache isn't kept: a settled pile stays within a fraction of a world unit, moving cats diverge a little; a restore is deterministic.
  - Written: after every profile write (a microtask later, so never in the middle of a tick: the wallet and the run's coins agree after a crash), on a run start, and with `GameSession.save()` (backgrounding, page hide). Cleared on game over, Quit to Menu and the debug Reset save.
  - Boot: `RunSaveStore.load()`; a stored run goes straight to the game screen (`GameSession.continueRun`: no `runStarted`, `runsPlayed` unchanged, the pause overlay up, a waiting pick under it). A snapshot of another version, unreadable, or refused by `restore` is removed with one warning and the menu opens. No migrations: bump `RUN_SAVE_VERSION` when the snapshot's shape or meaning changes. Batch 18 (v0.34) only added fields older snapshots can do without, so the version stays 1: a snapshot without them loads with the new picks at 0, no cracks and no shard mates, no echo used and no waiting pairs, the wind of its seed (`windDirectionOf`, the same roll a new run makes) and fresh Porcelain and Echo generators (an old run never rolled them); `tests/physics/run-v0.33.5.json`, written by v0.33.5, keeps it tested. Batch 19 does the same: without its fields a snapshot loads with no curse, the first one due at the 15th drop, and fresh curse and Dice generators; a curse on a ball that isn't a cat of sizes 1–6 in the jar is refused. (A v0.35.0 snapshot's `queue.follow`, the tier its later cats followed, is ignored.) `tests/physics/run-v0.34.0.json`, written by v0.34.0 with Batch 18's picks on, keeps that tested. Both fixtures are version 1: since v0.36 `decodeRunSave` drops them, and the tests read them with `decodeRunSave(text, 1)` to keep the shapes tested.
- Migrations: `MIGRATIONS[n]` turns version n data into version n + 1; they run in order up to `SAVE_VERSION`. A migrated save is rewritten in the new format right away.
- Repair: every known field is validated. Counts may exceed 2^53 (until v0.36 later stages' scores did), so their limit is the largest finite number. An upgrade level below its card's start level is repaired to it. A missing field silently takes its default, so adding a field needs no migration. An invalid field (wrong type, negative, above an upgrade's max level, …) takes its default or the nearest valid value and is reported. Unknown fields are dropped.
- Corrupt data (unreadable JSON, no version, a failed migration) and repaired saves: keep a copy of the raw text under `maneki-merge:save:corrupt:<timestamp>` (only the newest 3), then rewrite the save in clean form. A save from a newer app version is backed up the same way and loaded with the fields this version knows.
- Storage errors never crash the game: a failed read starts from defaults in memory, and `save()` returns false when a write fails (storage full or blocked).
- Write on:
  - purchase (`Profile.buy`: written at once, even inside the throttle window)
  - any change (coins, records, stats, settings, hints), throttled: the first change after a quiet second is written at once, later ones at most once per second (`SAVE_THROTTLE_MS`)
  - run end (game over, leaving to the menu)
  - `visibilitychange` (hidden) and `pagehide` (`Profile.flush()`)
- A refused write keeps the changes pending and is retried with the next change or flush. A hard kill without a page hide can lose at most the last second of changes.
- Call `navigator.storage.persist()` once (best effort).

## 9. PWA and offline

- Manifest:
  - name "Maneki Merge", short_name "Maneki"
  - `display: "fullscreen"` (iOS falls back to standalone), `orientation: "portrait"`
  - theme and background colours (from `config/app.ts`, cream `#fcefdf`); icons 64/192/512 + maskable 512; `apple-touch-icon` 180
  - icons are generated from the owner's `art-source/app-icon.*` (docs/ART_ASSETS.md §4.6) by `npm run icons` (`tools/buildAppIcon.ts`, also run by `npm run art`) and committed, so builds don't need `sharp`: the 64/192/512 and Apple 180 icons are the picture resized; the maskable 512 shrinks it to 86% and copies its edge pixels outwards, so the raised paw stays inside the 40% safe circle (v0.42.11; until then a code-drawn `public/icon.svg`)
  - iOS meta tags with the `default` status bar (dark text; the light theme would hide white status-bar text)
- Workbox `generateSW` precaches the whole build (JS, CSS, HTML, fonts, images, audio, and since v0.38 the how-it-works clips, `public/clips/*.mp4`, about 4 MB), with `navigateFallback` = `index.html`. There are no remote origins to cache.
- A clip is played from a blob URL (`ui/overlays/clipPopup.ts` fetches it whole): iOS asks for a video in byte ranges, which the precached response the service worker serves doesn't answer, so a plain `<video src>` would fail offline on iPhones.
- Every precached file has a revision (its content hash) except Vite's own output, whose name already holds one (`PRECACHE_HASHED_URL` in `config/app.ts`: `assets/<name>-<8-char hash>.<ext>`). The art keeps its file names under `assets/<kind>/`, so it needs the revision: a replaced image then reaches installed apps with the next update. Until v0.23.1 the plugin's default skipped revisions for all of `assets/`, so replaced art (like v0.23's NEXT bubble) stayed old on installed apps. A unit test checks every file in `public/assets/`.
- Updates use `registerType: "prompt"` so the app, not the plugin, decides when to switch. When a new service worker is waiting and the main menu has been idle (the menu screen, no shop or settings panel open) for `UPDATE_APPLY_DELAY_MS` (1 s, `config/platform.ts`), the app activates it (`skipWaiting`) and reloads on its own, showing an "Updating…" badge meanwhile. A version that arrives during a run waits until the player is back on the menu; the run is ended and saved before the reload. The delay matters: leaving a run calls `history.back()`, and Chromium never activates a worker told to skip waiting while that traversal is pending, so an immediate activation hung until the next launch. Never reload during a run. Until v0.23.3 the player had to tap an "Update ready" badge, and on phones a home-screen app is rarely cold-started, so updates often waited for days.
- `platform/updateGate.ts` owns this policy. The page's own `controllerchange` (when a worker already controlled it at boot) and the plugin's `onNeedReload` hook route through it, so even when another window of the app activates the update, this window doesn't reload mid-run: it reloads the next time its menu is idle. Tapping the badge retries a stalled activation. The plugin's hook alone missed launches (v0.42.14): it only listens once workbox has reported the version waiting, 200 ms after it installed, while the loading screen activates it as soon as it has installed; on a phone the switch came first, the app never reloaded and "Updating…" stayed on the menu (reproduced in Playwright with workbox's 200 ms stretched to 3 s: no reload; with the listener the app reloads on the loading screen).
- A long-running app checks for a new version when it becomes visible and once an hour (`config/platform.ts`).
- **Updates on the loading screen (v0.42.10, GAME_DESIGN §2.0).** When a service worker already controls the page (any launch after the first visit), boot registers it first and `launchUpdate` (`platform/pwa.ts`) asks the server for a new version beside the image loading (at most `UPDATE_LAUNCH_CHECK_MS`, 3 s, skipped offline). A version it finds installs meanwhile ("Updating…", at most `UPDATE_LAUNCH_INSTALL_MS`, 20 s). Until `finishLaunch` the gate is in its launch mode: nothing runs and no history traversal is pending, so a waiting version is activated at once and the app reloads as soon as it takes control, on the loading screen; if that hasn't happened within `UPDATE_LAUNCH_APPLY_MS` (5 s), the game opens and the menu applies it as above. A first visit registers the service worker last, as before, so its precaching (about 11 MB) doesn't slow the first loading.
- **The loading screen** (`index.html` draws and styles it, so it shows before the scripts; `ui/loadingScreen.ts` drives it). `preloadImages` (`game/artImages.ts`) loads and decodes every image in `public/assets/` and the clips' posters (`__PRELOAD_IMAGES__`, listed by `vite.config.ts` at build time) and fills the bar; one that fails or isn't in after `PRELOAD_TIMEOUT_MS` (10 s) is skipped. Every loaded image is kept for the app's lifetime, so the DOM's `<img>`s and CSS backgrounds with the same URL come from the browser's memory cache at once instead of the service worker (until v0.42.9 the coins, the score card, the NEXT bubble and the jars' backgrounds weren't waited for, and the Upgrades screen's decoded pieces were dropped, so they popped in late on phones). `loadArt` takes its images from the same cache. Chromium never finishes `img.decode()` in a hidden page (the desktop app's browser pane when hidden): drive it with Playwright's headless shell.

## 10. Mobile platform checklist

- `viewport-fit=cover`; no pinch or double-tap zoom (`touch-action: none` on the play area, block `gesturestart`); no text selection or long-press callout; `overscroll-behavior: none`; a fixed body so there's no rubber-band scrolling.
- Landscape on a phone shows a full-screen "Please rotate your device" overlay and pauses the run. "Phone" means a coarse pointer and a landscape viewport at most 540 px tall, so tablets in landscape stay playable.
- Audio (`audio/index.ts`): the AudioContext is created inside the first gesture (`pointerdown`, `pointerup`, `touchend`, `keydown`, captured on window) and resumed on every later gesture until it runs, with a one-sample silent buffer so iOS starts output; it is never created outside a gesture (`navigator.userActivation`), so no autoplay warning. iOS mutes web audio when the silent switch is on, which is acceptable.
- Mixer: each sound → its own gain (`config/audio.ts`) → master gain → a DynamicsCompressor used as a limiter → output. `VoiceThrottle` skips a sound started less than its `minIntervalMs` ago or with `maxVoices` still playing, and caps all voices at `MAX_VOICES`, so ten merges in one step play a pop or two, never a stack. Sound off suspends the context.
- Backgrounding: pause the run, save (the profile and the run in progress), and suspend audio; becoming visible resumes it (iOS may wait for the next tap).
- Android back button: history-state handling (game → pause → menu).
- WebGL context loss: recover by regenerating textures, without crashing.
- Haptics (`platform/haptics.ts`): use `navigator.vibrate` when it's available and enabled, with the patterns in `config/platform.ts`; merge ticks are rate-limited; turning haptics off cancels a running pattern; nothing on iOS (no API).
- Install hints: on an iOS browser outside standalone mode, show Share → Add to Home Screen. On Android, use `beforeinstallprompt`.

## 12. CI/CD

- Development happens directly on `main` (no side branches or PRs), so `deploy.yml`'s checks are the gate before every deploy. While the game is in development nobody else plays it, so the E2E suite does not gate the deploy (owner's decision, v0.23.1+): it reports failures afterwards.
- `ci.yml` runs on PRs and on pushes to branches other than main (kept for the rare case one is used): `npm ci` → typecheck → lint → format check → unit tests with coverage → build → Playwright (`npx playwright install --with-deps chromium webkit`).

## 13. Performance budgets

- 60 fps on mid-range phones (e.g. iPhone 11, Pixel 6a) with 150 cats; physics at most 4 ms per frame; no GC spikes.
- Old phones (v0.23.8): never less sharp on a phone that keeps up; a phone that can't may lose pixels (§6, adaptive resolution) but not stutter because of the renderer.
  - **No Graphics in the steady frame.** Phaser 4 re-traces every Graphics path each frame and cuts every arc into 100 points (a new object each), whatever its size: the 40-odd aim dots, the three rounded shine strips and the 21 rim dashes were about 5000 points and 70% of the render's CPU time (Chromium, CPU throttled 6× as a stand-in for an old phone: 4.5–5 ms of a 6.5–7.5 ms render, more than the physics' 2–3 ms). They are images now; since v0.42.12 the aim's ghost and the magnet's selection ring are too (ring textures), so the art skin draws no Graphics at all (the vector skin's danger caps and arm and the growing glass still are).
  - **One texture for the jar's cats.** On iOS and Android Phaser binds one texture per batch (`autoMobileTextures`), so with a texture per size every change of size in draw order cost a draw call: 29 per frame with 24 cats (Android emulation). The atlas draws the cats in one call: 9 per frame for the whole scene, whatever the number of cats. Pooled effects (rings, floating texts, particles) add a few while they play.
  - Together (same setup, about 25 cats, median of runs): the render took 2.5 ms instead of 4.6 and the whole frame's work 6.0 ms instead of 7.7. Pixel diffs of the same scenes before and after stay within 8/255 (the dots within 33/255 at their anti-aliased edge).
  - **Few images in the steady frame (v0.42.12).** Phaser 4 costs about the same per image whatever its size, so everything that is drawn every frame is as few images as it can be. A CPU profile of play (Chromium on the GPU, Android emulation, CPU throttled 6×, 13 cats) showed the aim guide alone at about a third of the frame's work: 33 dot images and the ghost, a Graphics circle re-traced every frame. The dots became one cropped column image and the ghost and the selection ring ring-texture images (§6); the rim's 21 dashes became one image. Production builds before and after, alternating, 4 runs each, the same pile (9 cats after its merges) and an aim moving all the time: frame work median 5.5 → 4.1 ms (4.9–6.4 → 3.6–4.8), mean 6.7 → 4.9, 90th percentile 11.2 → 8.1. Same-state canvas snapshots differ only at the rings' and the dashes' anti-aliased edges (at most 47/255; the selection ring's 71/255, a 100-sided polygon's edge against a true circle's), nothing else.
  - **No multisampling with the raster art (v0.42.12).** Every edge the art skin draws is inside a texture padded with transparent pixels (cats 2 px plus the atlas gap, sparks and glows fading to nothing at their edge, jar pieces cut at the art's own edge), so 4× MSAA smoothed nothing: with it off, the snapshots above match the cats, the jar and the paw pixel for pixel. It saves the multisampled colour and depth-stencil buffers: at 2.5× on a 390 × 844 screen (975 × 2110) about 58 MB of GPU memory, and the resolve every frame.
  - Physics in play is small next to the render: headless, a bot dropping every 0.6 s for 60 s of play (25 cats on average, 32 at most) costs 0.13 ms per tick on the dev machine; the 150-cat benchmark 0.86 ms. 60% of a step is matter-js's position solver and our Coulomb velocity solver, set by the iteration counts (§5).
- Gzipped JS under 800 KB; first load under 3 s on 4G; instant offline start afterwards.
- Final art: a WebP atlas, at most 4096×4096 in total (2048×2048 pages preferred).

## 16. Google Play app (v0.43)

The owner's call (2026-10-13): the Play app is a **Trusted Web Activity** (TWA) of the live site,
not the Capacitor wrapper M14 first planned. Chrome runs the site full screen inside the app, so
it behaves like the installed web app the owner tests on the phone, shares Chrome's storage for
the origin (the saves carry over), and gets game updates through the service worker (§9) without
a Play release. The costs: the first launch needs a connection (as a first visit does), and on a
phone whose browser can't host a TWA it opens as a Custom Tab with a URL bar. The owner's steps in
Play Console are docs/PLAY_STORE.md.

- **`android/`** is the Gradle project that Bubblewrap (`@bubblewrap/core` 1.27.0,
  `TwaGenerator.createTwaProject`) generated from `android/twa-manifest.json`: package
  `io.github.sekerderya.manekimerge` (permanent on Play), host `sekerderya.github.io`, start
  `/maneki-merge/`, `fullScopeUrl` the game's path (so only links into `/maneki-merge/` open the
  app), display `fullscreen` (immersive), portrait, every bar and the splash `#fcefdf`, no
  notification delegation, no permissions, the site-settings shortcut, Custom Tabs as the fallback,
  minSdk 24 (Android 7.0, what `androidbrowserhelper` needs), compile and target SDK 36, `androidbrowserhelper` 2.7.4, AGP 8.9.1, Gradle 8.11.1,
  versionCode 1 / versionName 1.0.0 (the wrapper's version, apart from the game's). The launcher
  icon is the maskable icon (adaptive), the splash and `store_icon.png` (Play's 512 icon) the 512
  icon, all fetched from the live site at generation time.
- **One change by hand:** `LauncherActivity.getDisplayMode()` returns immersive mode with
  `LAYOUT_IN_DISPLAY_CUTOUT_MODE_SHORT_EDGES`. Bubblewrap's "immersive" keeps the default cutout
  mode, which leaves a black band the camera cutout's height at the top of a full-screen app (the
  installed web app's v0.42.15 problem, §7). Whether Chrome then lays the game into the cutout can
  only be seen on a phone.
- **Regenerating** (a new Bubblewrap, a new icon or name): run `TwaGenerator.createTwaProject` on
  `android/twa-manifest.json` into an empty folder, copy it over `android/`, and put the
  LauncherActivity change back. A yearly target-SDK bump (Google's deadline is 31 August) can
  instead edit `compileSdkVersion` / `targetSdkVersion` in `android/app/build.gradle` (and AGP
  and Gradle if the new SDK needs them). Every Play upload needs a higher versionCode: raise it in
  `app/build.gradle` and `twa-manifest.json` together. Prettier skips the generated `android/app/`.
- **Digital Asset Links.** Chrome opens the app full screen only when
  `https://sekerderya.github.io/.well-known/assetlinks.json` names the app's package and the
  SHA-256 of a key it is signed with. The file has to be at the domain's root, so it lives in the
  owner's user-site repository `sekerderya/sekerderya.github.io` (Pages from `main`, with
  `.nojekyll` so the `.well-known` folder is served; the project sites under it are unaffected).
  It lists Play's app signing key (installs from Play) and the upload key (the APK installed
  directly). The app's side is `assetStatements` in `app/src/main/res/values/strings.xml`.
- **The upload key**: `npm run android:key` (`tools/android/createUploadKey.ts`) runs `keytool`
  (JAVA_HOME, the PATH or the usual Windows Java folders) for an RSA 2048 key, alias `upload`,
  PKCS12, valid 30 years, under `~/maneki-merge-upload-key/` with a random password beside it,
  never in the repository (`.gitignore` also ignores `*.p12`, `*.jks`, `*.keystore`). It stores
  the keystore (base64) and the password as the repository secrets
  `ANDROID_UPLOAD_KEYSTORE_BASE64` and `ANDROID_UPLOAD_KEYSTORE_PASSWORD` with `gh secret set`,
  and prints the fingerprint. It refuses to overwrite an existing key.
- **The build** (`.github/workflows/android.yml`): Ubuntu, Temurin 17, `./gradlew bundleRelease
assembleRelease`, `aapt2 dump badging` (the package, the SDK levels and the label in the log),
  then `jarsigner` signs the bundle and `zipalign` + `apksigner` the APK with the upload key, the
  job summary shows the key's fingerprint, and the artifact `maneki-merge-android`
  (`maneki-merge.aab`, `maneki-merge.apk`) is kept 30 days. Signing happens after Gradle, so the
  generated `build.gradle` has no signing config. Without the secrets it keeps the unsigned
  outputs and warns.
- **In the app** the page should match an app display mode (`standalone`, or `fullscreen` in
  immersive mode; not checked on a phone yet), so the install hints don't show
  (`platform/installContext.ts`); the back button, vibration and the update flow work as in the
  installed web app. The privacy policy Google Play asks for, in the app and on the listing, is
  `public/privacy.html` (precached), linked from Settings (GAME_DESIGN §2.4).
